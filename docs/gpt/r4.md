## 一、外部审查原文（按原文结构收录）

### 总体判断

fr-agent 已完成 I0～I6 主体，能从自然语言需求生成真实业务 CPT，也能对已有 CPT 做受控局部修改。
但在继续扩展前，有几处"表面成功、实际错误"的隐患必须先收口：

> 先确保现在已经支持的能力不会静默生成错误报表，也不会把模板修改的成功状态误报为成功。

### P1（必须先修）

**P1-1 Template Patch 的数据集描述符断层（真实链必被拒，离线测掩盖）**

- `TemplateLocator` 对 `replace_dataset` 的放行依据是 `descriptor.datasetNames`；
- 但 `TemplateInspector.describe()` 实际只返回 `{sheetCount, sheets}`，**不返回 `datasetNames`**；
- 因此真实链路里 `replace_dataset` 一定被 Locator 拒绝；离线测试因为**手工构造 descriptor**（自带
  `datasetNames`）而全部通过——测试构造了生产中不存在的输入形状，属"假绿"。

**P1-2 TemplateDiff 的 `clean` 判定过宽**

- `structDelta`（结构计数变化）没有纳入 `clean`；
- `tokens` 只提取 CDATA 文本，**属性值、非 CDATA 文本内容的变化会漏检**；
- 于是"未预期结构变化"或"属性值被改"都可能报 `clean=true`。

**P1-3 执行回归会假 PASS**

- `execGrid` 失败时返回的是错误字符串（不是网格），两侧都失败且错误串相同时被判定为相等 → PASS；
- `renderPng` 返回 `-1`（失败）时没有判失败；
- 结论：模板修改的"执行/渲染回归"可能把失败报成成功。

### P2（本轮应收口，不阻塞）

**P2-1 JOIN 基数守卫只依赖人工声明**

- `confirmed` 关系只校验"声明了 N:1/1:1"，未验证目标列是否真的是 PK/唯一键；
- 未校验方向与基数一致性、未检测目标记录重复；
- 若目标键实际重复，INNER JOIN 会 fan-out 放大度量，报表数字静默变大。

**P2-2 SQLBuilder 三处边界**

- `dateRange` 丢失日期维所属表，跨表时固定挂主表；
- JOIN 列限定依赖维度处理顺序（先处理的维度裸列、后处理才限定），结果随入参顺序变化；
- filter 操作符 × 字段类型没有约束：`==` 应映射为 SQL `=`，`like/contains` 不应许给数值列。

**P2-3 ReportSpec 能力清单过期**

- `ReportSpec.capabilities()` 仍报 chart unsupported、presentation 只有 table；
- SQL 分支的 `SpecValidator` 提前 `return`，**没有复用普通分支的 presentation 校验**（如 `showTotal`
  类型错误在 SQL 路不被拒绝）。

**P2-4 Planner 能力判断与实际能力脱节**

- Planner 的 SQL 分支把 `filters/sort/topN/presentation.chart` 一律丢弃或报"暂不支持"，
  而这些能力在 I5.3 已经落地——用户写了却被静默丢弃。

### 排期建议（审查给出）

I5.4（SQLBuilder 正确性收口）→ I6.1（Template Patch 集成可靠性）→ I5.5（Semantic Model 关系可信度）
→ I1.1（能力清单统一）。测试分三层：纯函数契约 / FineReport 对象读写集成 / 真实 CPT 执行+真值+渲染回归。

## 三、执行记录

### I6.1-A 数据集描述符断层（commit `a32ab05`）

- **根因**：`describe()` 与 `Locator` 之间没有共享"数据集存在性"的活接口。
- **修**：`describe()` 增加 `datasetNames` 与 `hasDataset(name)`（内部 `datasetExists(wb,name)` 活断言；
  FR 没有可靠的"枚举全部数据集名"API，故提供语义化断言而非伪造列表）；`Locator.replace_dataset`
  优先 `hasDataset`，回退静态 `datasetNames`（保持离线可测、零 `wb` 依赖）。
- **集成证据**：新增 `probes/probe_patch_dataset_integration.js`（真 WorkBook，runraw 路径）：
  `readCpt → describe → Locator 放行 → apply → export → 再读回`，数据集列数 4→2、首列类型
  `java.lang.Integer` 保真、原件未被写；8 项全 PASS，落 `data/i61_dataset_integration_truth.txt`。
- **测试补强**：`fast_template` +3 真实 describe 形态断言（`hasDataset` 优先于空 `datasetNames`、
  ghost 数据集拒）。

### I6.1-B 结构 diff 收紧（commit `faa2699`）

- **修**：
  - 关键属性签名多重集（`SEMANTIC_ATTRS`），过滤引擎内部 `Theme/Fork/TemplateId` 标记噪声；
  - `structDelta` 纳入 `clean`；
  - 按 op 分类：`replace_cell_value` 要求结构全守恒；`replace_dataset` 仅允许 `dataCols/tableData`
    结构变化 + 数据集本体 token 豁免（SQL/java 类/列名 CSV/行值/空占位），**单元格文本仍严格拒**。
- **教训**：首版豁免过宽（把任意 `''`/`dsN` 都放行）→ 收紧为白名单形态，并补"仍拒单元格文本"负测。

### I6.1-C 执行/渲染回归结构化（commit `faa2699`）

- **修**：新建 `template/regression.js` 纯函数裁决器：
  `execution(before,after,hasDatasetOp)` / `render(pngBefore,pngAfter)` 均返回结构化
  `{ok,grid|bytes,error}`；**任一失败即 FAIL，绝不比较错误文本**；标题变化只比数据区（跳过前两行）；
  渲染 `-1`/异常=FAIL。
- **测试**：`fast_template` 增"两边都失败同串→FAIL""数据区变化→FAIL""渲染失败→FAIL"等不变量；
  `execGrid` 兼容 `getValue/toString` 兜底（原 `getText` 非函数被 try 吞成假 PASS 的真实缺陷）。

### I5.4 SQLBuilder 正确性收口（commit `9ffc775`）

- **① JOIN 列限定顺序无关**：改两阶段——先解析全部维度收集 `{table,column}` 与 JOIN 集合，
  再统一按 `hasJoin` 生成 SELECT/GROUP BY/WHERE，消除"先处理的维度裸列、后处理才限定"的歧义。
- **② 跨表日期维**：`dateRange` 保留 `dateDim` 的 `{table,column}` 归属，WHERE 挂 `refTable` 而非固定主表。
- **③ op×类型约束**：语义 op→SQL op 统一映射（`==`→`=`，禁直出）；数值列拒 `like/contains`，
  文本列只允许 `OP_SQL` 映射集内的 op，其余结构化拒。
- **④ 受控字面量/单语句无分号**仍守（SQL_READONLY）。
- **验证**：`fast_sqlbuilder` +5 专项（顺序无关/跨表日期/`==` 映射/数值 like 拒/文本非法 op 拒）+ 全 12 套件 GREEN；
  引擎 live 双维 JOIN（bizDate+machine）`failures=0`，总计 33531/26531/79.12 不重不漏。

### I5.5 关系目标键唯一性机器验证（commit `5ac4ca3`）

- **修**：`ModelValidator.validate(model, schema, options)` 增加 `options.uniqueKeyEvidence`
  （数据侧唯一性探针结果注入，validator 仍零 IO/零 java）；confirmed N:1/1:1 关系的 to 侧键必须
  ∈ Schema 声明唯一键（PK / unique 单列索引）**或**有注入证据，否则 `UNSUPPORTED_RELATION_KEY` 拒；
  1:N / N:M 标 confirmed → `UNSUPPORTED_CARDINALITY` 拒。
- **证据**：`probes/probe_relation_unique.js` 实机只读：`laser_files.file_key rows=538 distinct=538
  unique=true`（VERDICT PASS，落 `data/i55_relation_unique_truth.txt`）；`make_api` SQL 生成前读该证据注入。
- **教训**：Java `Long` 对象身份比较使 `538==538` 误判 `unique=false` → `+rs.getLong()` 数值化后修正。
- **验证**：`fast_semantic` +3 项（无证据拒 / Schema 声明认可 / 1:N 误标拒）；引擎 live 日报
  `MODEL↔SCHEMA 通过` `failures=0`；12 套件 GREEN。

### I1.1 能力清单与校验单点（本轮，未单独 commit 前并入本批）

- **`lib/report_spec.js`**：`capabilities()` 改为按数据集种类分列且与实现一字对齐：
  - `datasets.rows`：sum + table(+showTotal)；chart/filters/sort/topN/join 明确 `unsupported`；
  - `datasets.sql`：table(+showTotal)、`chart{bar|pie|line}` via `presentation.chart`、
    `dateRange` + `dataset.filters`、`dataset.sort`、`dataset.topN`、confirmed 安全关系 INNER JOIN；
  - 兼容顶层旧字段保留真值、文案不再撒谎。
- **`lib/spec_validator.js`**：抽 `validatePresentation(rs, errs, isSql)` **一处真相**，两分支共用：
  - sql 分支此前提前 `return` 跳过 presentation 校验 → 现在 `showTotal` 非布尔、`heightsPt` 非数、
    `presentation.type` 越词表都会拒；
  - `presentation` 键白名单（未知键 `UNSUPPORTED_CAPABILITY`，防"写了没人管"）；
  - **rows 路 `presentation.chart` 明确拒**——`compile()` 根本不读它，旧行为是静默丢图。
- **`semantic/planner/planner.js`**：SQL 分支透传 `dataset.filters/sort/topN` 与
  `presentation.chart`（顶层 `chart` 也转入，`filters` 数组转 `dataset.filters`，位置写错给结构化 warning）；
  presentation 键**原样透传**（未知键交 validator 拒，planner 不再静默吞）。
- **测试**：`fast_report_spec` +9（sql 路 showTotal/heightsPt/type/未知键/chart 合法与缺值、rows 路 chart 拒、
  capabilities 两条）；`fast_planner` +6（filters/sort/topN 直通、chart 直通、顶层 chart 转换、
  顶层 filters 转 dataset.filters、非法 presentation 键→rejected）。
