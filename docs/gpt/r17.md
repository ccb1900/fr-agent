2. 发现的 P1 问题
P1-1：PID 检查和 Kill 之间仍然存在竞态
文件：agent/tools/_identity.ps1

当前逻辑：
$cur = ProcStartTicks $jp.pid

if ($jp.start -gt 0 -and $cur -ne $jp.start) {
    return 'spared'
}

$p = Get-Process -Id $jp.pid
$p.Kill()


问题是：
1. 第一次根据 PID 查询进程启动时间。
2. 第一次查询结束。
3. 原进程退出。
4. Windows 可能复用 PID。
5. 第二次 Get-Process 获取到另一个进程。
6. 直接 Kill。
也就是说，虽然代码验证了 PID + StartTime，但实际 Kill 的 Process 对象没有经过同一轮身份验证。

建议：
- 获取一次 Process 对象。
- 读取这个对象的 StartTime。
- 和记录的 StartTime 比较。
- 只有匹配才对这个对象执行 Kill。
- Kill 后在同一个对象上 WaitForExit。
不要先查一次 PID，再重新按 PID 获取进程后直接杀。
P1-2：无法区分进程不存在和进程身份无法读取
仍然是 _identity.ps1：
function ProcStartTicks([int]$procId) {
    if ($procId -le 0) { return -1 }
    try {
        $p = Get-Process -Id $procId -ErrorAction Stop
        return [long]$p.StartTime.Ticks
    } catch {
        return -1
    }
}


这里把所有异常都变成 -1。

但 -1 实际可能代表：
- 进程已经退出。
- PID 不存在。
- 权限不足。
- 无法读取 StartTime。
- 其他进程访问异常。
这些情况不能用同一个结果处理。

尤其 Kill-OrphanJvm：
if ($cur -lt 0) { return 'gone' }


如果进程还活着，但因为权限问题无法读取启动时间，代码会认为它已经消失。

随后 fr_agent.ps1 可能继续：
Remove-Item $cfg.FineDbLck


然后启动新的 FineReport。

这违背了 fail-closed 原则。

建议采用三态结果，而不是 bool 或 -1：
状态	意义	行为
Alive	确认是原进程且仍存活	按身份处理
Gone	确认原进程已经不存在	允许继续
Unknown	权限不足、信息不完整、无法判断	拒绝启动

这里不需要引入任何第三方依赖，使用 .NET Process 即可。
P1-3：java.pid 尚未写入时，存在孤儿 JVM 无法识别的窗口
文件：engine_launch.ps1

当前顺序：
$p = Start-Process @sp
$st = $p.StartTime.Ticks

[System.IO.File]::WriteAllText(
    $PidFile,
    ($p.Id.ToString() + ' ' + $st.ToString())
)

$p.WaitForExit()


注意：

Java 进程启动和 java.pid 持久化不是原子操作。

如果 PowerShell 恰好在 Start-Process 成功后、写入 PID 文件之前被强制终止：
- active.json 已经存在。
- Java 可能仍然存活。
- java.pid 不存在。
- 下一次执行识别出 owner 已退出。
- Read-JavaPid 返回 null。
- Kill-OrphanJvm 返回 gone。
- 新任务继续启动。
这会造成两个 FineReport JVM 同时运行。

这是一个真实的崩溃窗口，不能靠现有 S5 测试证明不存在。

我建议先不要自己发明新的恢复协议，而是评估 Windows Job Object 是否值得用于解决子进程生命周期管理。但这也不意味着必须引入它：可以先通过安全拒绝和更可靠的启动登记缩小风险。
P1-4：损坏的 java.pid 被当作进程不存在
当前：
if (-not (Test-Path $pf)) {
    return $null
}

$parts = ((Get-Content $pf -Raw -Encoding UTF8).Trim() -split ' ')


如果文件存在但内容损坏：
- PID 无法解析时返回 null。
- 上层把 null 解释成 gone。
- 继续清理 FineDB 锁并启动新任务。
这和损坏 active.json 时拒绝执行的策略不一致。

建议区分：
- 文件不存在。
- 文件合法。
- 文件存在但损坏。
- 文件无法读取。
后两种必须返回 Unknown，不能当作 Gone。
P1-5：finally 无条件删除 active.json
文件：agent/tools/fr_agent.ps1

当前：
try {
    $rc = & $RunBody
} finally {
    # release sentinel only if it is ours
    if ($cur -and [string]$cur.runId -eq $RunId) {
        Remove-Item $activeFile -Force
    }
}


这里虽然检查了 RunId，但没有确认 Java 进程已经退出。

如果 RunBody 发生异常，而 Java 仍然存活，finally 仍会删除 active.json。

下一次任务看到 active.json 不存在，就不会检查上次 Java 进程。

建议：只有确认本次 Java 已退出，才能清除活动哨兵。否则保留哨兵，让下一次任务安全拒绝。

3. 另外两个需要处理的问题
P2-1：相同 RunId 并发可能污染 Artifact
这次删除了 RUNID_INFLIGHT，但 fr_agent.ps1 仍允许调用者指定 RunId。

目前目录创建在 Mutex 之前：
$runDir = "$agentDir\runs\$RunId"
New-Item -ItemType Directory -Force -Path $runDir


同时 Artifact 组装已经移到 Mutex 外。

考虑以下情况：
1. 第一次调用 RunId=A，执行完 FineReport，释放 Mutex。
2. 第一次调用开始生成 artifact.json。
3. 第二次调用也使用 RunId=A，取得 Mutex。
4. 第二次覆盖同一目录中的 compile.json 或 patch.json。
5. 第一次 Artifact 组装读取到第二次的数据。
结果可能出现交叉污染。

GUID 默认生成只能降低概率，不能解决显式重复 RunId 的情况。

建议在入口处采用成熟的原子文件创建方式，对 RunId 做独占登记；或者明确禁止调用方指定已经存在的 RunId。

不需要恢复整套 OwnerToken 和队列系统。
P2-2：测试 S5/S5b 不是完整的真实宿主崩溃测试
我检查了 verify/integration_runtime.ps1。

S5 的做法是：
- 手动启动一个 Java decoy。
- 手动写入 java.pid。
- 手动写入一个已死亡 owner 的 active.json。
- 调用真实 create 流程。
这能验证身份化清理路径，但没有真实制造：

PowerShell 宿主在启动 Java 的过程中突然终止。

也没有覆盖前面提到的 Start-Process 和 PID 文件写入之间的窗口。

S5b 同样是预先写入 decoy 状态，而不是实际终止一个正在运行 patch 的宿主。

所以 README 中的“崩溃恢复全绿”，应该更准确地表述为：
人工构造遗留进程状态后的恢复路径通过测试。

这和真实宿主崩溃恢复完全可靠，是两回事。

5. 最终架构判断
我认为 R16 已经比 R14 合理很多。
应该保留的东西
- Windows Named Mutex
- .NET Process
- 统一 Java 启动器
- 极薄的 active.json
- FineReport Artifact 契约

应该继续收敛的东西
- 进程身份判断
- 异常退出状态处理
- 启动登记与进程生命周期之间的竞态
- RunId 独占

还有一个小问题：history.log 现在仍然参与测试的 MaxLiveRuntime 判断。它可以用来辅助诊断，但它不是内核互斥的证明。真正的互斥应该通过并发测试、实际进程数量和引擎入口观察来验证。

我的结论：R16 不回滚，R17 只修上述边界，不再重写 Runtime。
