我建议把下一阶段定义为 fr-agent 从报表生成引擎向 AI 报表创作引擎演进，而不是继续无边界地增加 FineReport 功能。

下面这份规范可以直接交给 Codex / Claude Code 执行。它不是重构愿景，而是按迭代拆分的工程任务，每个迭代都有明确范围、交付物、验收标准和禁止事项。

# fr-agent 下一阶段迭代规范

阶段目标

从人工编写 JS Spec 驱动，演进到结构化 ReportSpec 驱动，并最终实现自然语言创建真实业务报表。

核心链路

```
自然语言
    ↓
Agent
    ↓
Semantic Model
    ↓
ReportSpec
    ↓
ReportIR
    ↓
FineReport Object Graph
    ↓
CPT
    ↓
执行 / 渲染 / 验证
```

技术约束

- 保留 Windows + Java + Nashorn + FineReport 11。
- 保留 ES5、IIFE、`load()` 运行模式。
- 保留现有 `make_api.js` 和 `RunResult` 契约。
- 不重写 `object.js`，不重新发明 CPT 序列化。
- Agent 不直接生成或执行任意 Nashorn 代码。

## 迭代总览

| 迭代 | 名称               | 主要成果        | 优先级 |
| -- | ---------------- | ----------- | --- |
| I0 | 可靠性收尾            | 修复现有链路问题    | P0  |
| I1 | ReportSpec 接口    | 结构化输入、稳定输出  | P0  |
| I2 | Schema Inspector | 自动读取数据库结构   | P0  |
| I3 | Semantic Model   | 业务实体、指标、映射  | P0  |

| I5 | Agent 闭环         | 自然语言生成 CPT  | P1  |
| I6 | Template Patch   | 已有 CPT 局部修改 | P2  |

建议不要把七个迭代同时启动。前一个迭代的验收通过后再开始下一个。

# I0：现有生成链路可靠性收尾

P0 · 必须先完成

目标：确保现有生成器在错误输入、运行异常和安全边界情况下，能够可靠失败，而不是输出不完整或虚假的成功结果。

### 任务 0.1：IR 结构校验完整性

检查 `lib/ir.js` 所有入口和嵌套对象。

重点检查：

- `sheets`
- `blocks`
- `datasets`
- `columns`
- `filters`
- `widgets`
- `conditions`
- `floats`
- `toolbar.buttons`
- `charts`
- `links`

要求：

1. 所有数组字段必须验证为 Array。
2. 所有对象字段必须验证为 Object，且不能把数组当作普通对象接受。
3. 所有数值必须验证为有限数值。
4. 枚举值必须使用明确白名单。
5. 所有对象引用必须能够解析。
6. 所有错误必须包含 JSON 路径。

期望错误格式：

```
{
  "code": "INVALID_ARRAY",
  "path": "sheets[0].blocks",
  "message": "blocks must be an array"
}
```

不能因为用户输入一个错误类型，就导致校验器自身抛出 TypeError。

### 任务 0.2：Runner 阶段和失败结果统一

检查：

- `make_api.js`
- `runtime/bootstrap.js`
- `runtime/datasource.js`
- `lib/runresult.js`

要求：

- Runtime 初始化失败进入 RunResult。
- 数据库连接失败进入 RunResult。
- 执行失败不能继续部署。
- 渲染失败按照明确策略记录。
- 部署失败必须影响最终退出码。
- 所有提前退出路径均生成最终结果。
- 每个阶段只能有合法状态转换。

建议阶段：

```
input_load
runtime_initialize
datasource_connect
ir_validate
object_build
cpt_export
cpt_validate
execute
render
deploy
```

不要为了阶段数量而拆分过度，关键是错误不能逃逸统一结果契约。

### 任务 0.3：安全边界

完成：

- URL 协议相对路径检查。
- URL 目标策略明确化。
- 工具栏 Java 类名白名单。
- 图片文件路径限制。
- SQL 值参数绑定。
- SQL 标识符白名单。
- Agent 不接触数据库密码。
- 数据源只读策略。

### 任务 0.4：数据类型

增加并验证：

| IR 类型    | Java 类型              |
| -------- | -------------------- |
| integer  | Integer              |
| long     | Long                 |
| float    | Double               |
| decimal  | BigDecimal           |
| string   | String               |
| boolean  | Boolean              |
| date     | 对应 FineReport 日期类型   |
| datetime | 对应 FineReport 日期时间类型 |

具体 FineReport 日期对象映射必须通过实际运行探针确认，不能凭 Java 类型名称猜测。

### 验收标准

- 现有基线报表全部通过。
- 原有 CPT MD5 基线不发生非预期变化。
- 新增异常输入测试。
- 安全边界测试通过。
- 不发生失败但退出码为 0 的情况。
- Nashorn 环境实测通过。

禁止事项： 借本迭代重写 IR、Object、CPT 或 Runner 架构。

# I1：建立 ReportSpec 结构化输入接口

P0 · 自然语言接入的前提

目标：让 Agent 不再需要编写任意 JS Spec，而是提交一个受约束的 JSON 报表规格。

新增建议目录：

```
lib/
  report_spec.js
  spec_validator.js
  spec_compiler.js
schemas/
  report-spec.schema.json
examples/
  report-spec/
```

现有 `ir.js` 不要被 ReportSpec 逻辑污染。

### 1.1 定义 ReportSpec

建议初版结构：

```
{
  "version": "1.0",
  "report": {
    "name": "生产日报",
    "description": "按车间统计生产情况"
  },
  "dataset": {
    "source": "production_db",
    "query": {
      "type": "semantic"
    }
  },
  "dimensions": [
    {
      "field": "workshop",
      "label": "车间"
    }
  ],
  "metrics": [
    {
      "field": "plan_quantity",
      "label": "计划产量",
      "aggregation": "sum"
    },
    {
      "field": "actual_quantity",
      "label": "实际产量",
      "aggregation": "sum"
    },
    {
      "field": "completion_rate",
      "label": "完成率",
      "aggregation": "ratio_of_sums"
    }
  ],
  "filters": [
    {
      "field": "production_date",
      "type": "date_range",
      "default": "yesterday"
    },
    {
      "field": "workshop",
      "type": "multi_select"
    }
  ],
  "presentation": {
    "type": "table",
    "show_total": true
  }
}
```

这是逻辑示例，不是要求最终 Schema 必须采用这些字段名。

### 1.2 设计三个独立职责

| 模块             | 职责                    |
| -------------- | --------------------- |
| ReportSpec     | 表达用户想要什么报表            |
| Spec Validator | 检查结构和语义引用是否合法         |
| Spec Compiler  | 将 ReportSpec 转换成现有 IR |

不要把 ReportSpec 直接当作 IR。

两者的生命周期不同：

- ReportSpec 是用户需求和 Agent 设计的表达。
- ReportIR 是 FineReport 后端能够执行的结构化中间表示。

### 1.3 建立机器调用入口

新增：

```
make_spec.js
```

或在现有 Runner 上增加明确的 JSON 输入模式。

接口必须支持：

```
输入：ReportSpec.json
输出：RunResult.json + CPT
```

要求：

- 继续支持旧 JS Spec。
- 新旧入口互不破坏。
- 支持指定输出目录。
- 不允许 Agent 指定任意文件系统输出位置。
- 支持只生成、不执行的模式。
- 支持完整执行和渲染模式。

### 验收标准

1. 现有 `sales_demo.js` 仍然可用。
2. 一个 JSON ReportSpec 能生成同等功能的报表。
3. 不需要用户编写 Nashorn 代码。
4. 无效 ReportSpec 能返回结构化错误。
5. 同一个 ReportSpec 多次执行结果稳定。

# I2：Schema Inspector 数据库结构检查器

P0 · 业务语义层的数据基础

目标：Agent 能够了解数据库里有什么，而不是凭字段名猜测。

新增：

```
semantic/
  schema/
    inspector.js
    metadata.js
    relation.js
    serializer.js
```

建议不要把它塞进 `object.js` 或 `datasource.js`。

### 2.1 第一阶段只读元数据

支持获取：

- 数据库类型。
- Schema。
- 表和视图。
- 字段名称。
- 字段类型。
- 是否允许 NULL。
- 主键。
- 外键。
- 索引。
- 表间关联。

优先支持你现有实际使用的 SQL Server。

其他数据库通过 Adapter 扩展，不要提前建设多个没有验证的驱动。

### 2.2 输出标准化 Schema

示例：

```
{
  "source": "production_db",
  "tables": [
    {
      "name": "production_order",
      "columns": [
        {
          "name": "plan_qty",
          "type": "decimal",
          "nullable": false
        },
        {
          "name": "workshop_id",
          "type": "int",
          "nullable": false
        }
      ],
      "primaryKey": ["id"],
      "foreignKeys": [
        {
          "column": "workshop_id",
          "references": "workshop.id"
        }
      ]
    }
  ]
}
```

### 2.3 数据采样

可选支持有限的数据样本，用于帮助 Agent 理解字段。

但要有约束：

- 默认关闭。
- 明确限制行数。
- 只读取经过授权的表。
- 对敏感字段进行脱敏。
- 不把业务数据样本写进普通日志。
- 不允许模型自由构造扫描全库的 SQL。

### 验收标准

给定一个真实 SQL Server 数据源，系统可以输出完整、准确的结构描述。

并能区分：

- 结构事实；
- 外键推导关系；
- 尚未确认的业务关系。

这三个不能混为一谈。

# I3：轻量 Semantic Model

P0 · 核心差异化能力

目标：把数据库字段转换为 Agent 能够理解的业务概念。

建议目录：

```
semantic/
  model.js
  entity.js
  relationship.js
  metric.js
  dimension.js
  mapping.js
  validator.js
  resolver.js
models/
  production/
    model.yaml
```

我建议这个模块独立于 FineReport。

未来即使换成其他报表引擎，业务语义模型仍然可以复用。

### 3.1 需要支持的对象

| 对象           | 含义           |
| ------------ | ------------ |
| Entity       | 业务实体         |
| Property     | 业务属性         |
| Relationship | 实体之间的关系      |
| Metric       | 业务指标         |
| Dimension    | 分析维度         |
| Mapping      | 业务属性与数据库字段映射 |
| Rule         | 业务规则         |

### 3.2 指标定义必须明确

例如：

```
metrics:
  completion_rate:
    label: 生产完成率
    expression:
      type: ratio
      numerator:
        field: actual_quantity
        aggregation: sum
      denominator:
        field: plan_quantity
        aggregation: sum
    format:
      type: percent
      precision: 2
```

这比简单存储：

```
formula: actual_quantity / plan_quantity
```

可靠得多。

因为它明确了聚合语义。

### 3.3 必须支持语义映射置信度

例如：

```
用户说：实际产量

数据库字段：
  actual_qty
  good_qty
  completed_qty
```

系统不能直接选择其中一个。

建议返回：

```
{
  "status": "ambiguous",
  "candidates": [
    {
      "field": "actual_qty",
      "reason": "字段名匹配"
    },
    {
      "field": "good_qty",
      "reason": "字段名及业务标签匹配"
    }
  ],
  "requires_confirmation": true
}
```

注意：置信度只能作为排序依据，不能替代业务确认。

### 验收标准

完成一个真实业务领域模型，例如生产管理。

至少定义：

- 5 个业务实体；
- 10 个属性映射；
- 3 个实体关系；
- 5 个指标；
- 3 个维度；
- 业务歧义处理。

所有映射必须可以追溯到数据库字段。

# I4：Report Planner 自然语言需求转换器

P1 · 引入 Agent 能力

目标：把自然语言转换成 ReportSpec，而不是让大模型直接生成 CPT。

这部分不建议你自己实现 Agent 框架。

使用现有 Codex、Claude Code 等 Agent，fr-agent 提供确定性的工具接口。

### 4.1 Planner 的输入

```
用户需求
+
数据库 Schema
+
Semantic Model
+
fr-agent Capability
```

### 4.2 Planner 的输出

```
ReportSpec
+
Assumptions
+
UnresolvedQuestions
+
ValidationWarnings
```

例如：

用户：

> 做一个最近七天各车间生产完成率的日报。

Agent 输出：

```
{
  "report": {
    "name": "近七天车间生产日报"
  },
  "dimensions": [
    "workshop",
    "production_date"
  ],
  "metrics": [
    "plan_quantity",
    "actual_quantity",
    "completion_rate"
  ],
  "filters": [
    {
      "field": "production_date",
      "default": "last_7_days"
    }
  ]
}
```

如果完成率的分子定义不清楚，就不能直接进入生成阶段。

### 4.3 追问策略

只追问影响正确性的歧义：

- 指标口径不明确。
- 多个字段可能代表同一业务概念。
- 数据关联关系不确定。
- 数据粒度不一致。
- 需求超过当前后端能力。

不需要追问：

- 默认字体是什么。
- 表头使用什么颜色。
- 普通列宽是多少。
- 每个单元格放在哪里。

这些应该由 Agent 根据产品设计规则自行决定。

### 验收标准

准备 20 条真实业务需求：

- 明确需求能够自动生成 ReportSpec。
- 模糊需求能够正确追问。
- 不支持的需求能够明确拒绝。
- 不能产生未定义的数据字段。
- 不允许静默编造业务指标。

# I5：自然语言创建 CPT 完整闭环

P1 · 产品核心里程碑

目标：用户不接触 JSON、不接触 SQL、不接触 IR，也不需要理解 FineReport API，就能生成一张可用的报表。

交互：

```
用户提出需求
    ↓
Agent 获取 Schema
    ↓
Agent 加载 Semantic Model
    ↓
生成 ReportSpec
    ↓
校验并确认歧义
    ↓
调用 fr-agent
    ↓
生成 CPT
    ↓
FineReport 执行
    ↓
PNG 预览
    ↓
结构和数据验证
    ↓
交付 CPT
```

### 5.1 必须有验证闭环

不允许只根据 `RunResult.success === true` 就认为报表正确。

至少包含：

| 验证                   | 说明              |
| -------------------- | --------------- |
| Schema Validation    | 数据字段存在          |
| IR Validation        | IR 合法           |
| Build Validation     | 对象图构建成功         |
| CPT Validation       | CPT 文件合法        |
| Execution Validation | FineReport 执行成功 |
| Data Validation      | 结果数据符合业务口径      |
| Render Validation    | 报表能正常渲染         |

其中 Data Validation 最重要，也最容易被忽略。

例如完成率必须和独立 SQL 基准结果进行比较，而不是只检查图表有没有显示。

### 5.2 失败后允许 Agent 修复

例如：

```
第一次生成
    ↓
执行失败：字段类型不兼容
    ↓
RunResult 返回错误
    ↓
Agent 修正 ReportSpec
    ↓
第二次生成
    ↓
验证通过
```

必须限制：

- 最大修复次数；
- 单次生成时间；
- SQL 查询范围；
- 可修改的字段；
- 输出目录。

禁止无限循环。

### 验收标准

选一张真实生产报表，从自然语言到 CPT 全自动生成。

要求：

- 不人工编写 SQL；
- 不人工编写 JS Spec；
- 不人工修改 IR；
- 数据口径正确；
- FineReport 可以正常打开；
- 报表可以正常渲染；
- 生成结果可重复。

# I6：已有 CPT 的修改能力

P2 · 不要提前开发

目标：让 Agent 能够在已有 CPT 上执行受控修改，而不是重新生成一个看起来相似的报表。

新增：

```
template/
  reader.js
  inspector.js
  locator.js
  patch.js
  diff.js
  validator.js
```

### 6.1 先实现模板对象读取

验证能否通过 FineReport API：

- 读取现有 CPT。
- 获取 WorkBook。
- 枚举 Sheet。
- 枚举 Cell。
- 获取数据集。
- 获取参数。
- 获取公式。
- 获取图表和控件。

这里必须先做实机探针，不能根据 `TemplateWorkBookIO.readTemplateWorkBook()` 能读入模板，就认为对象访问能力已经完整。

### 6.2 定义 Patch 操作

第一版只支持：

| 操作                      | 说明      |
| ----------------------- | ------- |
| `set_report_title`      | 修改报表标题  |
| `set_cell_style`        | 修改单元格样式 |
| `set_column_width`      | 修改列宽    |
| `add_column`            | 增加列     |
| `remove_column`         | 删除列     |
| `add_filter`            | 增加筛选条件  |
| `change_filter_default` | 修改筛选默认值 |

暂不支持：

- 任意修改公式。
- 自动重构所有数据集。
- 任意跨 Sheet 移动对象。
- 自动重建复杂报表。
- 修改不认识的对象。

### 6.3 必须有差异和回滚

修改流程：

```
original.cpt
     ↓
Read
     ↓
Patch Plan
     ↓
Apply
     ↓
modified.cpt
     ↓
Structural Diff
     ↓
Execution Regression
     ↓
Render Regression
```

原始文件永远保留。

对于无法识别的原始对象，默认保持不动，而不是删除。

### 验收标准

选取 5 张真实历史 CPT：

- 读取成功。
- 定位目标对象。
- 完成至少一种局部修改。
- 导出修改后的 CPT。
- 原有查询、参数和图表功能不回归。
- 视觉差异在预期范围内。

# 八、所有迭代统一的工程纪律

这一部分建议直接放进项目 `AGENTS.md`，成为后续编码 Agent 的执行规则。

1\. 先读源码，再动手

- 必须读取相关模块完整实现。
- 不允许根据 README 推断实现情况。
- 不允许仅凭 Git 历史判断功能是否完成。
- 修改前先确认现有调用链和兼容性。

2\. 每个迭代先形成实施计划

先列出：

- 涉及文件；
- 当前行为；
- 目标行为；
- 数据结构变更；
- 兼容性风险；
- 测试方案。

计划通过后再修改。

3\. 必须保护既有能力

- 现有 JS Spec 继续可用。
- 不改变 Nashorn 兼容性。
- 不改变原有 CPT 序列化规则。
- 不随意改变 IR 字段语义。
- 不破坏原有 Runner 调用协议。

4\. 每项能力必须有真实验证

优先级：

1. 单元测试。
2. 结构测试。
3. FineReport 对象构建测试。
4. CPT 序列化测试。
5. FineReport 实机执行。
6. 数据正确性测试。
7. PNG 渲染回归。

5\. 禁止为了架构完整而提前抽象

当前不做：

- 自己开发 Agent 框架；
- 多 Agent 编排；

## 我的最终建议

不要把这次迭代理解成“给 fr-agent 增加 AI 功能”。

真正需要完成的是三个能力：

1. 知道数据是什么： Schema Inspector。
2. 知道业务是什么意思： Semantic Model。
3. 知道如何生成报表： ReportSpec → IR → FineReport。

这三者完成之后，Agent 才真正有条件把自然语言转换成可信的 CPT。

而已有 CPT 修改是另一条独立技术路线，应该放在自然语言新建报表闭环跑通之后。
