我的总体判断：

这两个问题比新增功能更重要。

## 1. R10：Agent 创作链有实质性进步

这次我认可的改进有四项。

| 改进                         | 价值                       |
| -------------------------- | ------------------------ |
| 每次请求独立 RunId               | 避免旧结果污染新任务               |
| 每个任务独立产物目录                 | 避免 compile、patch 互相覆盖    |
| capability_manifest 四层能力状态 | 区分构造、序列化、渲染和 Agent 可用性   |
| plan 接入 Planner            | Agent 可以先理解意图、判断能力，再创建报表 |

尤其是能力状态：

```
constructable
serializable
renderable
agentAvailable
```

这个设计值得保留。

它解决了一个很重要的问题：FineReport API 能创建某个对象，不等于这个对象能正确序列化，更不等于 Agent 可以安全地承诺用户这个功能可用。

这符合 fr-agent 的长期产品方向。

但这里还有一个需要持续注意的边界：

`discover` 返回的能力状态必须来自真实验证证据，而不是简单地根据 IR 枚举或 API 存在性推导。

## 2. R11：每次任务独立目录是正确的

这次新增的：

```
logs/agent/runs/{runId}/
```

是必要的。

特别是模板修改：

```
runs/
  run-a/
    patch.json
    patch.log
    staging/
      manifest.json

  run-b/
    patch.json
    patch.log
    staging/
      manifest.json
```

之前多个 Patch 任务共享 staging 目录，存在产物串扰的风险。

现在通过：

```
$env:TEMPLATE_STAGING = $stagingDir
```

实现每个任务独立 staging。

这不仅解决了并发污染，也让失败诊断、任务追踪、产物验收有了统一的身份。

另外，`runId` 字符集限制和严格验收也值得保留。

不过，建议未来将 RunId 的生成、验证、目录创建和产物归属校验进一步统一，不要让各个 verb 分别实现。

## 3. R12：Runtime Supervisor 是这次最重要的架构变化

以前的执行模型大致是：

```
Agent A ──→ PowerShell ──→ Java / FineReport
Agent B ──→ PowerShell ──→ Java / FineReport
Agent C ──→ PowerShell ──→ Java / FineReport
```

多个请求可能同时启动 FineReport。

但你之前已经明确过一个重要约束：底层 FineReport 不支持多实例同时运行。

因此，不能简单地把 Agent 并发等同于 FineReport 并发。

现在的模型变成：

External AI Agents

Agent A / Agent B / Agent C

fr_agent.ps1

独立 RunId、独立任务产物

## Runtime Supervisor

Global Lock

全局执行权

Queue

等待任务

History

执行事件

Single FineReport Runtime

同一时间最多执行一个引擎任务

这个方向我赞成。

它实现了：

- Agent 请求可以并发提交。
- FineReport 引擎任务串行执行。
- 任务可以排队。
- 任务失败不应该影响后续任务。
- 崩溃后可以识别遗留任务。
- 任务产物仍然独立。

这是比单纯在 `run.ps1` 前面加一个互斥锁更完整的方案。

### 但是，我发现两个 P1 问题

P1-A：锁初始化竞态

看 `runtime.ps1`：

```
New-Item -ItemType Directory -Path $lockDir -ErrorAction Stop

$ownerPid = if ($OwnerPid -gt 0) {
    $OwnerPid
} else {
    $PID
}

WriteJsonAtomic $currentFile @{
    runId = $RunId
    verb = $Verb
    pid = $ownerPid
    startedAt = (Get-Date).ToString('o')
}
```

这里先创建锁目录，再写 `current.json`。

问题是，这两个操作不是原子的。

可能出现以下时序：

| 时间 | 任务 A               | 任务 B                      |
| -- | ------------------ | ------------------------- |
| T1 | 成功创建 lock 目录       |                           |
| T2 | 尚未写入 current.json  | 尝试创建 lock，失败              |
| T3 |                    | 检查 LockIsStale            |
| T4 |                    | 因为 current.json 不存在，判断锁过期 |
| T5 |                    | 删除 lock 目录                |
| T6 | A 继续写 current.json |                           |
| T7 | B 重新创建 lock        |                           |

最终可能出现两个任务都认为自己拥有执行权。

这正是 Runtime Supervisor 最不能出现的情况。

建议修改：

锁的创建和所有权登记需要具备可验证的初始化协议。

可以采用：

1. 原子创建锁目录。
2. 在锁目录内部创建唯一 owner token 文件。
3. 通过原子文件创建确认初始化权。
4. 完成 current 状态写入。
5. 其他进程遇到初始化中的锁，只能等待，不能因为暂时没有 current.json 就删除锁。
6. 初始化超时必须经过单独的恢复判定。

更重要的是，释放和恢复操作都必须校验 owner token，不能只看 RunId。

P1-B：MaxLockAgeSec 可能误杀正常任务

当前代码：

```
function LockIsStale() {
    if (-not (Test-Path $currentFile)) {
        return $true
    }

    $cur = ReadJson $currentFile

    if (-not $cur) {
        return $true
    }

    if (-not (OwnerAlive $cur.pid)) {
        return $true
    }

    try {
        $age = ((Get-Date) -
            [datetime]::Parse($cur.startedAt)).TotalSeconds

        if ($age -gt $MaxLockAgeSec) {
            return $true
        }
    } catch {
        return $true
    }

    return $false
}
```

这里有一个逻辑问题：

即使 OwnerPid 对应的 PowerShell 进程还活着，只要任务执行时间超过 1800 秒，就会被判定为 stale。

随后 `Invoke-Recovery` 会：

```
Get-Process java |
    Stop-Process -Force

Remove-Item $lck -Force
```

也就是说，一个执行超过 30 分钟、但仍然正常运行的 FineReport 任务，可能被另一个等待任务判定为过期并杀掉。

报表生成、复杂模板渲染、数据量较大的 SQL 查询，都不应该被固定的 30 分钟上限直接判定为死亡。

我建议严格区分：

| 状态                | 判定       | 允许 Recovery |
| ----------------- | -------- | ----------- |
| Owner PID 已死亡     | 进程不存在    | 是           |
| Owner PID 仍存活     | 正常存活     | 否           |
| Owner PID 存活但疑似卡死 | 需要额外健康检查 | 暂不允许直接杀     |
| 锁初始化不完整           | 状态未知     | 经过专门恢复协议    |
| 任务执行超时            | 超出任务 SLA | 先标记超时，走受控取消 |

`MaxLockAgeSec` 应该是异常告警或任务超时参考，不应该直接等价于 Owner 死亡。

这是我认为当前必须优先修复的问题。

## 4. 另外三个值得改进的地方

### P2-A：Runtime Supervisor 目前仍然是文件系统状态机

当前状态存储：

```
logs/agent/runtime/
├── lock/
├── current.json
├── queue/
├── done/
└── history.log
```

对于单机、单实例的 FineReport 环境，这是合理的，不需要为了架构好看就引入 Redis 或数据库。

但是需要明确：

- queue 文件不是天然可靠的消息队列。
- history.log 不是天然可靠的事务日志。
- current.json 与 lock 目录之间没有事务保证。
- 文件系统操作可能因为异常退出而只完成一半。

建议将状态机定义为正式契约：

```
SUBMITTED
    ↓
QUEUED
    ↓
ACQUIRED
    ↓
RUNNING
    ↓
SUCCEEDED / FAILED
```

异常路径：

```
RUNNING
    ↓
RUNTIME_LOST
    ↓
RECOVERY
    ↓
FAILED
```

还需要定义：

- 同一 RunId 重复提交怎么办？
- 已经完成的 RunId 是否允许重新执行？
- 队列任务是否有明确的 FIFO 顺序？
- Supervisor 重启后如何恢复队列？
- `release` 在任务失败时如何记录失败状态？

尤其要注意：当前 `release` 将队列状态设置成 `done`，而业务实际执行成功或失败，是由 `fr_agent.ps1` 另外判断的。

这两个状态不应该混为一谈。

建议明确区分：

`runtimeState` 和 `businessResult`。

例如：

```
{
  "runtimeState": "released",
  "businessResult": "failed",
  "runId": "abc123"
}
```

这样不会把“执行权正常释放”误解为“报表生成成功”。

### P2-B：OwnerPid 仍然不是完整的进程身份

这次修复了 `$PID` 自动变量冲突，这是非常重要的。

但是 Windows PID 会被重复利用。

例如：

1. 原来的 PowerShell 进程退出。
2. Windows 回收 PID。
3. 新进程获得相同 PID。
4. Supervisor 误以为旧 Owner 仍然存活。

建议使用：

```
OwnerPid + ProcessStartTime
```

双重确认进程身份。

还可以加入：

```
RunId
OwnerToken
StartedAt
Heartbeat
```

但我不建议现在就把 Supervisor 做成复杂的分布式调度器。

单机系统不需要过度设计。

### P2-C：运行环境配置仍然分散

目前 `runtime.ps1`、`fr_agent.ps1`、`run.ps1` 仍有：

```
$ROOT = 'D:\fineagent'
$FR = 'D:\software\FineReport_11.0'
```

这是之前脚本治理讨论中已经指出的问题。

现在又增加了 Runtime Supervisor，意味着配置分散的维护成本更高了。

建议统一到一个配置入口：

```
agent/tools/
├── config.ps1
├── runtime.ps1
└── fr_agent.ps1
```

由 `config.ps1` 提供：

- 项目根目录。
- FineReport 安装目录。
- Java 路径。
- Nashorn 路径。
- Runtime 状态目录。
- 默认 Heap。
- 任务超时策略。

不要在每个入口重新声明。

## 5. 我还发现一个架构层面的遗漏：当前 Queue 不是真正的 FIFO 队列

这是一个容易被提交说明掩盖的问题。

当前 `runtime.ps1` 的 acquire 逻辑：

```
while ($true) {
    try {
        New-Item -ItemType Directory -Path $lockDir
        # 获取成功
        exit 0
    } catch {
        Start-Sleep -Milliseconds 250
    }
}
```

每个等待者都在轮询同一个锁目录。

虽然每个任务都注册了：

```
queue/{runId}.json
```

但实际获取执行权时，并没有按照 `submittedAt` 排序，也没有一个专门的 Dispatcher 负责分发任务。

因此：

- A 先提交，不保证 A 先执行。
- B 后提交，可能因为轮询时机先获得锁。
- queue 目前更像任务登记表，而不是真正的 FIFO 调度器。

这不是说当前串行执行无效。它能限制正常情况下的并发获取，但不能据此宣称已经实现严格的 FIFO 队列。

我的建议是先明确产品要求：

如果只需要串行执行，当前模型可以保留，接受非严格顺序。

如果需要提交顺序可预测，则需要单一调度者负责从队列中选取下一个任务，而不是让所有等待者竞争锁。

## 6. 一个额外的安全问题：Recovery 杀 Java 的范围太大

当前：

```
Get-Process java |
    Stop-Process -Force
```

这会终止机器上所有 Java 进程。

即使 OwnerPid 已经死亡，也不能证明所有 Java 进程都是这个任务启动的。

建议在启动 FineReport JVM 时记录：

```
Runtime Owner
Java PID
Java ProcessStartTime
RunId
```

Recovery 只能清理与当前 Runtime 所有权明确关联的 JVM。

FineDB 锁文件也一样，必须先确认当前 FineReport 实例已经退出，不能仅凭 PowerShell Owner 进程死亡就删除锁文件。

当前 `integration_runtime.ps1` 已经有 S1～S8，尤其 S8 用真实并发请求验证了单实例执行，这是很好的。

但我认为还缺以下测试：

| 测试                          | 预期结果           |
| --------------------------- | -------------- |
| S9：锁目录创建后、current 写入前发生并发竞争 | 不允许双重获取        |

## 8. 下一轮迭代建议

我不建议再扩大 Runtime Supervisor 的功能范围。

先把它收口。

## 9. 对整个项目的重新评价

这次更新让我对 fr-agent 的定位有了一个更明确的判断。

它已经不再只是：

```
自然语言 → JSON → CPT
```

而是在形成：

```
自然语言
    ↓
Agent 理解和规划
    ↓
语义模型与能力发现
    ↓
ReportSpec / Template Patch
    ↓
IR
    ↓
FineReport Object
    ↓
CPT
    ↓
Runtime Supervisor
    ↓
执行、验证、验收
```

这条链路才是你真正需要的产品。

我尤其认可三个方向：

1. Agent 负责创作，用户负责验收。
2. 能力必须有真实引擎证据，不能凭 API 猜测。
3. Agent 可以并发工作，但 FineReport 引擎必须受控串行运行。

但也有一个战略性提醒：

现在不要因为已经有了 Runtime Supervisor，就继续往里面加入任务中心、持久化调度、分布式队列、重试引擎等功能。

你当前的核心竞争力不是做一个通用任务调度平台，而是让 AI 真正能够创建和修改 FineReport 报表。

我给这次更新的评价：架构方向明显进步，但 R12 尚未达到可以放心交给多个 Agent 长时间自动运行的程度。

先修复两个并发 P1，再通过新增集成测试证明它们确实不会复发。其他功能可以暂缓。

最后，我认为有一个值得坚持的原则：

不要把 GREEN 当成正确性的证明。要让每一条关键不变量，都有一个能够主动制造故障、并证明系统正确拒绝错误状态的测试。

这比再增加十个新功能更有价值。
