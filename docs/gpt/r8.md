## 零、结论摘要

fr-agent 的底层技术路线已经相当清晰，但整个项目还没有形成一个真正统一的产品架构。现在最值得处理的不是继续修补 Validator，而是解决已有能力之间的组织关系。

四个值得认真对待的全局问题：

1. 主生成链和语义创作链之间存在架构断层。
2. 报表 IR 与 ReportSpec 的关系还不够统一。
3. 两套报表创建体系和已有报表修改体系尚未形成统一工作流。
4. 测试、探针、历史资产和正式产品代码之间的边界还不够清晰。

## 一、先还原整个项目的真实架构

目前仓库已经不只是一个 CPT 生成器。可归纳为六个能力域。

### ① Agent 创作层

`docs/agent-*` · 外部 Agent · Planner

自然语言需求 → 业务意图 → 报表规划

### ② 语义层

`semantic/schema` · `model` · `planner` · `query`

数据结构发现 → 业务本体 → 指标维度解析 → SQL

### ③ 报表描述与编译层

ReportSpec · IR · Object · CPT

业务规格 → 报表结构 → FineReport 对象图 → CPT

### ④ 引擎运行层

`runtime` · `make_api.js` · FineReport

数据连接 → 引擎初始化 → 执行 → 渲染

### ⑤ 修改与验证层

`template` · `verify` · `semantic/closure`

模板修改 → 结构验证 → 数据验证 → 视觉验证

### ⑥ 交付层（尚未统一）

CPT · PNG · PDF · RESULT_JSON · staging

最终结果、质量报告和用户验收

这张图是更接近产品目标的组织方式。

但注意：这是架构目标视图，不是说目前代码已经按照这六层完整实现。

### 当前真实模块归属

| 目录 | 实际职责 | 判断 |
| --- | --- | --- |
| `reports/` | 演示及业务报表规格 | 应保留 |
| `reports_prod/` | 生产报表生成规格 | 应保留，需明确资产管理 |
| `features/` | 数据浏览器业务生成器 | 目前只有一个主要 Feature |
| `lib/` | IR、对象图、CPT、ReportSpec | 职责开始偏多 |
| `runtime/` | 引擎激活、连接、路径 | 边界合理 |
| `semantic/` | Schema、Model、Planner、SQL、LoopGuard、Preflight | 核心价值很高 |
| `template/` | CPT 读回、修改、回归 | 独立边界合理 |
| `verify/` | 测试及业务真值验证 | 需要分层 |
| `probes/` | FineReport API 考古、引擎实验 | 历史资产过多 |

## 二、P0：最大的问题是创作链与生成链尚未真正统一

这是整个项目最值得优先处理的问题。

目前存在两条路径。

**路径 A：传统报表生成**

```
reports/*.js
    ↓
Feature
    ↓
IR
    ↓
Object
    ↓
CPT
    ↓
FineReport
```

**路径 B：AI 语义报表生成**

```
自然语言
    ↓
外部 Agent
    ↓
Planner
    ↓
ReportSpec JSON
    ↓
SpecValidator
    ↓
SpecCompiler
    ↓
SqlBuilder
    ↓
IR
    ↓
Object
    ↓
CPT
```

表面上两条路径可以汇合到 IR。

但问题是：目前它们的业务描述模型还没有成为统一的产品契约。

- `reports/*.js` 直接使用业务 Feature 的 JavaScript 规格。
- `ReportSpec` 使用另一套 JSON 声明式规格。

这意味着：

- 两套入口。
- 两种业务描述方式。
- 两种验证路径。
- 两种能力声明方式。
- 可能出现功能只在其中一条路径支持的情况。

这不是立即要删除其中一套，而是需要明确分工。

**建议**：ReportSpec 应该成为未来 AI 创作的标准业务契约，IR 成为所有报表生成方式的统一编译输入。

传统 JS Feature 可以继续存在，但逐渐成为兼容适配器，而不是第二套长期演进的产品协议。

目标：

```
                  Agent
                    │
                    ▼
               ReportSpec
                    │
         ┌──────────┴──────────┐
         │                     │
    Semantic Resolver      SpecValidator
         │                     │
         └──────────┬──────────┘
                    │
                SpecCompiler
                    │
                    ▼
                   IR
                    │
                 Obj.build
                    │
                   CPT
```

重要原则：

语义层负责解释业务含义，不应该再创建一套自己的报表结构语言。
IR 负责表达报表结构，不应该知道什么是 `InspectionRecord`、什么是 `completionRate`。

两者必须严格分工。

## 三、P1：lib 目录已经出现职责混合

当前：

```
lib/
  browser.js
  cpt.js
  dbpass.js
  index.js
  ir.js
  isodate.js
  object.js
  report_spec.js
  runresult.js
  spec_compiler.js
  spec_validator.js
```

这些文件实际上属于不同层次。

| 文件 | 实际性质 |
| --- | --- |
| `ir.js` | 报表中间表示及编译 |
| `object.js` | FineReport 后端 |
| `cpt.js` | CPT 产物验证 |
| `report_spec.js` | 业务描述契约 |
| `spec_compiler.js` | ReportSpec 到 IR 的转换 |
| `spec_validator.js` | 规格验证 |
| `isodate.js` | 通用领域值验证 |
| `runresult.js` | 执行结果契约 |
| `browser.js` | 历史兼容入口 |
| `dbpass.js` | 环境凭据基础设施 |

这里不是说必须马上移动文件，而是已经存在一个重要问题：lib 不再是一个语义明确的模块，而是一个历史上逐渐积累的公共代码目录。

建议逐步调整为：

```
lib/
  index.js

spec/
  report_spec.js
  validator.js
  compiler.js
  schema.json

ir/
  ir.js
  validator.js

backend/
  finereport/
    object.js
    cpt.js

common/
  isodate.js
  runresult.js

runtime/
  ...
```

但不建议立即执行目录搬迁。先建立真正的模块接口，再迁移路径。否则只是把文件换个位置，依赖关系仍然混乱。

### 还有一个值得注意的问题：`lib/index.js`

当前它是 CORE 门面，但 Runner 仍然直接加载：

```
load(Paths.lib('object.js'));
load(Paths.lib('ir.js'));
load(Paths.lib('cpt.js'));
```

这意味着门面尚未真正成为依赖入口。建议未来由：

```
CORE.Ir.compile(...)
CORE.Obj.build(...)
CORE.Cpt.validate(...)
```

统一对外提供能力。但要等到 Nashorn 全局兼容、加载顺序、Node 测试都经过验证后再切换。

## 四、P1：Semantic 内部已经有了不错的分层，但产品边界还需要重新定义

目前 Semantic 包含：

```
semantic/
  closure/
    loopguard.js

  model/
    evidence.js
    registry.js
    resolver.js
    validator.js
    vocab.js

  planner/
    capability.js
    planner.js

  query/
    sqlbuilder.js

  schema/
    inspect_main.js
    inspector.js
    metadata.js
    relation.js
    serializer.js

  preflight.js
```

这是整个项目最有长期价值的部分之一。尤其是：

- Schema 是物理结构事实。
- Model 是业务语义。
- Resolver 处理术语歧义。
- Planner 处理结构化意图。
- SQLBuilder 只编译受控语义。
- Preflight 负责编译前检查。
- LoopGuard 负责执行结果的下一步裁决。

这些职责基本合理。

但有一个架构问题：Semantic 目前既像一个独立可复用的业务语义引擎，又像报表编译器的前置子系统。两种定位需要明确。

**建议**定位为 `Report Intelligence Layer`（报表智能层）。

它不应该拥有 FineReport 的概念，也不应该直接负责 CPT。它应该提供：

```
discoverSchema()
resolveBusinessTerm()
resolveRelation()
resolveMetric()
planReport()
compileQuery()
validateSemanticContext()
```

然后由报表编译层消费它。

### 关于本体论，再强调一次

从现在的代码看，`models/production/model.json` 已经承担了一部分轻量本体的角色：

- 实体。
- 维度。
- 指标。
- 关系。
- 业务表达式。
- 业务名称映射。

不建议现在上完整 OWL、RDF 或复杂知识图谱。但建议把业务模型从单纯的 JSON 配置升级成明确的业务语义契约，例如：

```
{
  "name": "completionRate",
  "label": "完成率",
  "kind": "ratio",
  "numerator": "done",
  "denominator": "planned",
  "unit": "%",
  "aggregation": "recalculate"
}
```

尤其要明确指标的聚合语义。完成率不能简单地把每天的完成率求和或平均。这类约束应由模型保证，而不是依赖 Agent 每次正确理解。

## 五、P1：Template 与 Generate 目前是两套独立产品能力

当前：

```
生成：
ReportSpec → IR → Object → CPT

修改：
CPT → WorkBook → Patch → CPT
```

这两条路线独立是正确的。不建议强行做 CPT → IR 反编译。FineReport 的 CPT 不一定能无损恢复原始业务意图，之前 ABR-1 的边界设计也明确避免了这个方向。

但从产品角度看，用户不会认为这是两个不同的工具。用户只会说：

- 创建一张新报表。
- 修改这张报表。
- 增加一列。
- 修改标题。
- 改成按日期汇总。
- 增加一个图表。
- 调整展示格式。

所以需要一个统一的上层工作流：**Report Authoring Workflow**

- **Create**：新建报表
- **Modify**：修改已有报表
- **Duplicate**：基于模板创建
- **Validate**：执行和验收
- **统一交付契约**

**ReportArtifact**

- `artifactId`
- `sourceType`：generated / patched / duplicated
- `cptPath`
- `executionResult`
- `validationResult`
- `previewFiles`
- `diagnostics`

这个 `ReportArtifact` 是建议未来增加的统一产物契约。不必现在创建复杂的持久化工作流引擎。先让 Create 和 Modify 两种执行路径能够产生相同形态的结果，就已经很有价值。

## 六、P1：Runner 正在成为项目中的隐性架构中心

目前根目录有：

```
make_api.js
make_report.js
make_verify.js
make_pixel_diff.js
run.ps1
runraw.ps1
tools_br_run.ps1
tools_prod_run.ps1
```

其中 `make_api.js` 不只是启动器，它已经承担：

- 模块装载。
- 环境初始化。
- 数据连接。
- ReportSpec 处理。
- SemanticPreflight。
- SQL 编译。
- 对象构建。
- 执行。
- 渲染。
- CPT 导出。
- 凭据检查。
- 结果记录。

它已经是一个比较重的应用编排器。

问题在于，如果继续增加 Agent 工具接口、模板修改、自动修复和交付管理，最终它可能成为整个项目的上帝对象。

**建议**未来引入一个非常薄的应用服务层：

```
application/
  create_report.js
  modify_report.js
  validate_report.js
  preview_report.js
  contracts.js
```

这里不是要把 `make_api.js` 立刻拆成几十个文件，而是逐渐让 Runner 只负责：

1. 读取输入。
2. 调用 Application Service。
3. 输出结构化结果。
4. 处理进程退出码。

尤其不要让 Agent 直接依赖 `make_api.js` 内部变量或日志格式。Agent 应该消费稳定的 `RunResult` 和 `ReportArtifact`。

## 七、P2：探针和历史资产已经需要治理

这一点是全局审查才容易看到的问题。

当前 `probes/` 有大量文件：

- `_probe*.js`
- `probe_vanchart*.js`
- `probe_webpage*.js`
- `probe_widgets*.js`
- 各种数据库和 API 探针。
- 多个临时 PowerShell 扫描脚本。

370 个文件中，探针目录占据了相当大的比例。

这些文件不是垃圾。事实上，FineReport API 考古是项目最重要的技术资产之一。但现在需要区分三种性质：

| 类型 | 处理方式 |
| --- | --- |
| 一次性探索脚本 | 归档 |
| 可重复验证的能力探针 | 保留，登记运行条件 |
| 正式回归测试 | 移入或整理进 verify/tests |

建议：

```
tests/
  unit/
  integration/
  engine/
  regression/

research/
  probes/
  evidence/
  archive/
```

这次不要求搬迁全部历史文件。首先建立清单，标记哪些探针仍然是正式能力的唯一证据。

另外，`reports_prod/` 和 `reports/` 有不少同名业务报表。生产报表必须保留独立版本和部署规则，但建议明确公共规格、环境差异、生产专属逻辑之间的边界，避免两套代码长期漂移。

## 八、一个容易忽视的全局问题：架构文档之间的口径

对照了：

- `README.md`
- `AGENTS.md`
- `docs/architecture/boundaries.md`
- `docs/architecture/dependency-rules.md`
- `docs/agent-closure-interface.md`
- `docs/agent-planner-interface.md`

发现文档的演进方向并没有完全同步。

例如，ABR-1 文档把 Semantic 描述为独立旁路、不属于主生成链；而 Agent 闭环文档又把 Planner、SpecValidator、SpecCompiler、SQLBuilder 串成了真正的报表创作链。

这两个说法在不同阶段可以同时成立，但现在需要统一表达：

- Semantic 与底层 Core 依赖解耦。
- Semantic 在 AI 创作流程中参与报表生成。
- Agent 是外部编排者。
- Application 层负责把这些确定性能力组合起来。

这才是准确的整体架构。

另一个问题是 README 非常庞大，已经同时承担了：产品介绍、架构说明、FineReport API 考古、实验记录、运行手册、设计经验、历史事故记录。

建议保留一手事实，但把它们逐渐拆成可检索的技术手册，而不是让 README 无限膨胀。

## 十一、下一阶段怎么做：三个迭代，而不是十个小修补

### A1：统一创作契约

**目标**：让 Create 和 Modify 进入同一套产品接口。

**具体工作**：

1. 定义 `ReportArtifact`。
2. 定义统一 `RunResult`。
3. ReportSpec 和 PatchSpec 明确各自边界。
4. 统一诊断格式。
5. 定义 Create、Modify、Validate、Preview 四种操作。

**验收**：

- 创建报表与修改报表都返回相同结构的产物结果。
- Agent 不需要解析控制台日志判断成功。
- 失败时能明确定位到业务、语义、编译、执行或验证阶段。
- 原始 CPT 永远不被意外覆盖。

### A2：统一 ReportSpec → IR

**目标**：让所有新报表最终走统一编译入口。

**具体工作**：

1. 梳理现有 JS Feature 的规格表达能力。
2. 明确 ReportSpec 的能力覆盖范围。
3. 把可以表达的 JS Feature 逐步转换为 ReportSpec。
4. 不能表达的能力明确登记，不做静默降级。
5. 保留旧路径作为回归对照。

**验收**：

- 选取至少 5 种不同类型的现有报表。

## 十三、更直接的判断

fr-agent 当前状态分三个层面：

**底层工程能力** —— 已有较强基础。IR、对象图、CPT、Schema、SQL、模板修改、FineReport 执行与验证。

**系统架构完整性** —— 需要整合。创作入口、应用编排、产物契约、Agent 接口尚未形成统一体系。

**产品价值闭环** —— 尚待验证。还需要证明 Agent 能够独立完成真实业务报表，而不只是调用几个底层工具。

核心意见：fr-agent 下一阶段不应该继续以 Compiler 为中心组织所有工作，而应该以 **Report Authoring（报表创作）** 为中心组织产品。

Compiler 是重要基础设施，但不是最终产品。用户真正购买的不是一个 CPT 生成器，而是：

> 告诉 AI 我要什么报表，AI 理解业务、找到数据、创建或修改报表、执行验证，最后交付一份真正可用的 FineReport 报表。

这决定了后续架构应该围绕 Create、Modify、Validate、Preview、Deliver 组织。

**若现在决定开发顺序：A1 统一创作契约 → A3 现有 Agent 接入 → A2 逐步统一 ReportSpec。**

原因是：先证明产品闭环有价值，再决定哪些底层抽象值得进一步统一。不要为了一个尚未验证的理想架构，提前重构已经能够工作的代码。
