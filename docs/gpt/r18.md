### 审查结论

R17 的方向是对的，但目前不能判定 Runtime 已经安全收口。 它确实修复了 R16 的几个关键问题：身份判断改为三态、验证和 Kill 使用同一个 `Process` 对象、引擎启动前写入 `PENDING`、异常退出时保留活动哨兵，并增加了真实宿主终止测试。

但我在新代码中发现了两个更直接的 fail-open 缺口，恰好位于这次重点修复的进程身份和启动登记边界：

* `java.pid` 中的非法数值组合仍可能被当成合法身份，进而误杀其他进程。

* Java 已经启动、但读取启动时间或写入 PID 文件失败时，代码会删除 `PENDING`，把"可能已有孤儿 JVM"伪装成"从未启动"。

这两项都应当在继续扩大测试或整理文档之前修复。

### 1\. P1：PID 文件允许无效启动时间，可能误杀无关进程

文件：`agent/tools/_identity.ps1`，`Read-JavaPid()`；`Get-ClassifiedProcess()`。

当前解析逻辑：

```powershell
if ($parts.Count -lt 2 -or -not [int]::TryParse($parts[0], [ref]$jpid)) {
    return @{ file = 'corrupt'; pid = 0; start = -1 }
}
$jstart = -1
if (-not [long]::TryParse($parts[1], [ref]$jstart)) {
    return @{ file = 'corrupt'; pid = 0; start = -1 }
}
return @{ file = 'ok'; pid = $jpid; start = $jstart }
```

问题在于：能转换成整数，不代表它是合法的进程身份。

例如：

```text
1234 -1
```

会被解析成 `file = 'ok'`。

后续 `Get-ClassifiedProcess()` 有这段逻辑：

```powershell
if ($expectStart -le 0) {
    return @{ state = 'alive'; proc = $p }
}
```

也就是说，只要 PID 1234 当前存在，就会被认定为目标 Java。`Kill-OrphanJvm()` 随后可能直接 Kill 它。

这正好绕过了 R17 想建立的身份保护。

修复要求：

* PID 必须大于 0。

* StartTime 必须大于 0。

* 必须恰好有两个字段。

* 格式不符合要求，一律 `corrupt`，不能进入进程判断。

* Java 身份判断不允许使用 `expectStart <= 0` 的 PID-only 降级方式。

注意：`ownerStart = -1` 是另一种语义，可以继续用于 owner 的保守存活判断；不能把它和 Java 的可杀进程身份混为一谈。

建议新增测试：

| 输入                   | 预期      |
| -------------------- | ------- |
| 1234 123456789       | 合法      |
| 1234 -1              | corrupt |
| 1234 0               | corrupt |
| 0 123456789          | corrupt |
| -1 123456789         | corrupt |
| 1234 123456789 extra | corrupt |

S21 目前只测了 `not-a-jvm-id`，没有覆盖这些能够通过整数转换的非法身份。这是测试盲区。

### 2\. P1：启动成功后的登记失败，会删除 PENDING

文件：`engine_launch.ps1`，`Start-EngineJava()`。

这是我认为 R17 最需要优先修复的问题。

当前代码把三个操作放在同一个 `try` 中：

```powershell
try {
    $p = Start-Process @sp
    $st = -1
    try { $st = $p.StartTime.Ticks } catch { }
    [System.IO.File]::WriteAllText(
        $PidFile,
        ($p.Id.ToString() + ' ' + $st.ToString()),
        (New-Object System.Text.UTF8Encoding($false))
    )
} catch {
    Remove-Item $PidFile -Force -ErrorAction SilentlyContinue
    return 1
}
```

这里至少有两条危险路径。

路径 A：StartTime 读取失败

`Start-Process` 已经成功，Java 已经启动。

但读取 `StartTime` 失败后，代码把 `$st` 留为 `-1`，仍然写入 PID 文件。

这会直接触发上面第一个 P1：无效身份被当作合法身份。

路径 B：PID 文件写入失败

`Start-Process` 已经成功，Java 已经启动。

随后 `WriteAllText()` 失败，进入外层 catch：

```powershell
Remove-Item $PidFile -Force
```

这会把 PENDING 删除。

然后回到 `fr_agent.ps1`：

```powershell
$javaGone = Confirm-RunJavaGone $cfg.RunsDir $RunId
```

因为 PID 文件已经不存在，`Confirm-RunJavaGone()` 返回 `$true`，最终清除 `active.json`。

但是 Java 可能仍然活着。

下一次任务就可能重新启动 FineReport，产生第二个 JVM。

这与 R17 的核心目标直接冲突。

正确的最小修复：

把启动失败和登记失败分开处理：

* `Start-Process` 明确失败，才能考虑撤销 PENDING。

* `Start-Process` 成功之后，任何身份读取或 PID 持久化失败，都不能直接删除 PENDING。

* 如果能够通过已经取得的 `$p` 对象安全终止进程，并且 `WaitForExit` 确认退出，才可以清理登记。

* 如果不能确认退出，就保留 PENDING，让下一次任务拒绝执行。

核心原则：

一旦可能已经启动 Java，就不能再用"删除 PID 文件"表达"没有启动 Java"。

这不是增加新设施，只是修正现有异常处理的边界。

### 3\. P1：Named Mutex 的作用域还需要明确

文件：`agent/tools/config.ps1`。

目前默认名称：

```powershell
MutexName = 'fr-agent-fine-report-runtime'
```

Windows 下未指定 `Global\` 的命名 Mutex 默认属于当前 Session 的命名对象命名空间。

因此需要明确一个部署约束：

* 如果所有调用方保证在同一个 Windows 登录 Session 内运行，当前方案可以成立。

* 如果桌面程序、计划任务、服务或不同登录 Session 都可能调用，就不能直接把当前 Mutex 当成整台机器的互斥锁。

不同 Session 可能各自取得同名 Local Mutex。此时共享 `active.json` 也不能完全补救：两个调用方可能同时读到没有活动哨兵，然后分别写入自己的哨兵并启动 Java。

我的建议不是立刻引入复杂的锁协议，而是先明确产品运行边界：

如果要求整台机器单实例，就评估 `Global\` 命名 Mutex，并验证不同 Session 的创建权限和 ACL。

如果明确只支持单 Session，则把这个约束写进运行契约和验收测试。

### 4\. P2：RunId 的 create-new 语义尚未被充分证明

文件：`agent/tools/fr_agent.ps1`。

当前流程：

```powershell
if (Test-Path $runDir) {
    ...
}
try {
    New-Item -ItemType Directory -Path $runDir -ErrorAction Stop | Out-Null
} catch {
    ...

```

它比原来的 `New-Item -Force` 好，但提交说明把它称为 create-new 原子独占，需要更严谨的验证。

目前 S23 是连续执行两次相同 RunId，验证第二次拒绝。这只验证了顺序重复，没有验证两个进程同时通过 `Test-Path` 的竞争窗口。

我不建议仅凭注释就认定这里已经具备原子独占语义。

建议增加一个并发测试：两个独立 PowerShell 进程同时申请同一个 RunId，必须只有一个成功，另一个明确得到 `RUNID_EXISTS`，并验证目录中的产物没有交叉写入。

如果现有 `New-Item` 不能提供所需的独占语义，再用一个简单的 `FileMode.CreateNew` 预留文件解决，不需要恢复 OwnerToken 或队列系统。

### 6\. 全局架构判断

架构方向保留

我没有看到需要推翻 R16/R17 架构的理由。

目前仍然应该坚持：

```text
外部调用
   │
   ▼
fr_agent.ps1
   │
   ▼
Named Mutex
   │
   ├── 检查 active.json
   ├── 检查遗留 Java 身份
   ├── 必要时 Kill + WaitForExit
   ├── 写入 active.json
   │
   ▼
run.ps1 / runraw.ps1
   │
   ▼
engine_launch.ps1
   │
   ▼
FineReport Java
   │
   ▼
释放哨兵 / 保留 HOLD
```

我不建议现在：

* 改成 TypeScript。

* 引入新的 Agent 框架。

* 自研 Supervisor。

* 引入数据库、队列或调度器。

* 重写整个 Runtime。

* 把 PowerShell 全面替换成 C#。

当前问题不是语言能力不足，而是几个关键异常路径没有做到严格的 fail-closed。

另外，`run.ps1` 中的 `Get-Process java | Stop-Process` 仍然存在，但 Agent 路径传入了 `-NoKill`，所以它不是本次发现的 Agent Runtime 双 JVM 问题。手动运行路径仍然有全局结束 Java 进程的副作用，后续应该单独明确它的使用边界。
