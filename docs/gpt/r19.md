### 二、新发现：P1，文件访问失败可能被误判为文件不存在

涉及三个位置：

* `agent/tools/_identity.ps1`：`Read-JavaPid()`，约第 77 行。

* `agent/tools/fr_agent.ps1`：`Invoke-UnderMutex()`，约第 82 行。

* `agent/tools/runtime.ps1`：status 分支，约第 19 行。

当前代码：

```powershell
if (-not (Test-Path $pf)) {
    return @{ file = 'absent'; pid = 0; start = -1 }
}
```

以及：

```powershell
if (Test-Path $activeFile) {
    # 读取 active.json
}
```

问题在于：`Test-Path` 的 false 不应被直接当作"不存在"的充分证据。

当路径访问遇到权限问题或文件系统错误时，PowerShell 的路径检查可能产生非终止错误并返回 false。当前全局 `$ErrorActionPreference = 'Continue'`，没有把这种情况转化成 `unknown`。

这会产生一个危险的状态转换：

```text
active.json 实际存在
       │
       ▼
路径检查遇到访问错误
       │
       ▼
Test-Path 返回 false
       │
       ▼
程序认为没有 active.json
       │
       ▼
继续申请执行权
       │
       ▼
可能启动第二个 FineReport JVM
```

`java.pid` 也有相同问题：

```text
java.pid 存在但无法确认是否可访问
       │
       ▼
Test-Path false
       │
       ▼
Read-JavaPid 返回 absent
       │
       ▼
Kill-OrphanJvm 返回 gone
```

这与 R17/R18 的 fail-closed 原则冲突。

建议修改：

不要用简单的 `Test-Path` 结果承担文件状态分类。

用能够区分以下结果的文件访问方式：

| 结果            | 应当分类为      |
| ------------- | ---------- |
| 文件明确不存在       | absent     |
| 文件存在且可读取      | 继续解析       |
| 文件存在但无权读取     | unreadable |
| 文件系统错误、状态无法确认 | unknown    |

可以使用 .NET 文件系统 API，在异常类型和路径状态明确的情况下分类。不要用 `File.Exists()` 简单替换 `Test-Path`，因为它同样可能把访问错误折叠成 false。

这个问题应该优先修复。 它不是新架构，只是把文件状态判断补齐。

### 三、P2：Collect-UnregisteredSpawn 有一个正常退出竞态

文件：`engine_launch.ps1`

当前实现：

```powershell
function Collect-UnregisteredSpawn($p, [string]$PidFile) {
    $confirmed = $false
    try {
        $p.Kill()
        if ($p.WaitForExit(15000)) {
            $confirmed = $true
        }
    } catch {
        $confirmed = $false
    }

    if ($confirmed) {
        Remove-Item $PidFile -Force -ErrorAction SilentlyContinue
        return 'confirmed'
    }

    return 'kept-pending'
}
```

考虑一种情况：

* Java 已经启动。

* 进程很快自然退出。

* PowerShell 读取 `StartTime` 失败。

* `Collect-UnregisteredSpawn` 开始回收。

* `$p.Kill()` 因为进程已经退出而抛出 `InvalidOperationException`。

* catch 直接判定 `confirmed = false`。

结果是：

明明 Java 已经退出，程序却留下 PENDING，导致下一次任务持续 RUNTIME_BUSY。

这是安全方向的保守错误，不会因此启动第二个 JVM，但会产生不必要的人工恢复问题。

建议调整为：

* Kill 成功或失败，都继续尝试 `WaitForExit`。

* `WaitForExit` 确认退出，才允许清理 PENDING。

* 无法确认退出，继续保留 PENDING。

这里不需要额外状态，也不需要引入新的组件。

### 二、新发现：P2，`runtime.ps1` 会把未知文件状态显示成 absent

建议修复

文件：`agent/tools/runtime.ps1`，第 27–32 行。

当前逻辑：

```powershell
$javaState = 'absent'
$jp = Read-JavaPid $cfg.RunsDir ([string]$a.runId)

if ($jp.file -eq 'ok') {
    $javaState = Classify-Process ([int]$jp.pid) ([long]$jp.start) $true
}
elseif ($jp.file -eq 'pending') {
    $javaState = 'unknown'
}
elseif ($jp.file -eq 'corrupt') {
    $javaState = 'corrupt'
}
elseif ($jp.file -eq 'unreadable') {
    $javaState = 'unknown'
}
```

R19 的 `Read-JavaPid` 已经可能返回：

```text
absent
readable → 后续解析为 ok
unreadable
unknown
pending
corrupt
```

但这里没有处理 `unknown`。

于是：

```text
java.pid 存在，但文件状态无法确认
       ↓
Read-JavaPid 返回 unknown
       ↓
runtime.ps1 没有匹配分支
       ↓
javaState 保留初始值 absent
```

这不会直接导致第二个 JVM，因为 `runtime.ps1` 只是只读状态工具。但它会给运维人员一个错误的诊断结果，和 R19 刚建立的文件状态原则相矛盾。

建议：改成穷尽式状态映射，未知状态默认输出 unknown，而不是 absent。

例如：

```powershell
switch ($jp.file) {
    'absent'     { $javaState = 'absent' }
    'ok'         { $javaState = Classify-Process ([int]$jp.pid) ([long]$jp.start) $true }
    'pending'    { $javaState = 'unknown' }
    'corrupt'    { $javaState = 'corrupt' }
    'unreadable' { $javaState = 'unknown' }
    default      { $javaState = 'unknown' }
}
```

这项修改不涉及 Runtime 架构调整。
