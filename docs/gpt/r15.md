那么这个约束就可以作为架构决策的硬边界了：

单机、单个 FineReport 实例，同一时刻最多执行一个任务。任务可以来自多个调用方，但必须串行进入 FineReport。

这意味着我们不需要通用分布式调度系统，也不需要自己实现一个复杂的任务队列。

## 1. 我建议的目标方案

多个调用方

PowerShell / Agent / CLI / 自动化任务

单实例执行入口

统一获取 Named Mutex

FineReport Runtime

同一时刻只有一个任务

启动 / 等待 / 结果检查 / 释放互斥

FineReport 实例

## 2. 具体采用什么成熟方案

我建议第一版只采用：

- 跨进程互斥： `.NET System.Threading.Mutex`，使用 Windows Named Mutex。
- 进程管理： `.NET System.Diagnostics.Process`。
- 超时控制： .NET 等待机制及 CancellationToken。
- 结果持久化： 普通 JSON 文件，仅保存必要的执行结果和诊断信息。

不引入：

- Redis
- SQLite
- Hangfire
- Quartz.NET
- Windows Service
- 自制 FIFO 调度器
- 自制分布式锁
- 通用任务队列框架

这些都不是当前约束所必需的。

## 3. 当前 R14 哪些东西应该重新评估

| 现有机制               | 建议                          |
| ------------------ | --------------------------- |
| Named Mutex        | 保留                          |
| `queue/`           | 优先考虑删除                      |
| `owner.json`       | 评估是否可以删除，不能为了恢复而保留复杂协议      |
| `recover-previous` | 重新设计，不允许任意调用者触发危险恢复         |
| OwnerToken         | 如果不再有队列所有权概念，考虑删除           |
| FIFO               | 不承诺，除非业务明确要求                |
| 崩溃恢复               | 仅处理实际存在的遗留进程和 FineReport 状态 |

这里需要特别注意：Mutex 被操作系统自动释放，不代表 FineReport 的 Java 进程也会自动退出。

例如 PowerShell 宿主崩溃，但它启动的 Java 进程仍然存活。下一次调用虽然能取得 Mutex，却不能因此直接启动另一个任务。

因此，必须有一个很薄的遗留进程检测机制。它应该通过可靠的进程身份信息识别自己启动的 Java 进程，而不是扫描所有 Java 进程，更不能无条件杀进程。

## 4. 我认为最合理的任务执行流程

1. 获取 Named Mutex。
2. 检查是否存在上一次遗留的 FineReport 执行进程。
3. 如果存在，判断其状态；无法确认时拒绝启动新任务。
4. 启动当前任务。
5. 等待 Java 进程结束。
6. 验证退出状态和 FineReport 执行结果。
7. 清理本次运行资源。
8. 释放 Mutex。

这就是一个单实例执行器，不需要包装成任务调度平台。

## 5. 下一步应该做什么

我建议对 `fr-agent` 当前整个仓库做一次以删除自研基础设施为目标的架构审查，而不是继续在 R14 上打补丁。

最终输出应该只有四类决策：

- 保留： 确实解决 FineReport 特有问题的代码。
- 替换： 已有成熟 .NET / Windows 实现的功能。
- 删除： 没有实际需求、重复或过度设计的机制。
- 补充： 成熟组件无法解决的 FineReport 特有边界。

有一点我会坚持：在核对当前仓库代码前，不直接断言 `queue/` 和 `owner.json` 一定可以删除。我们需要检查它们是否承担了遗留进程识别、执行结果追踪等不可替代的职责。

架构目标：让 Runtime 尽可能薄，让开发精力回到 AI 报表生成、修改和验证上。
