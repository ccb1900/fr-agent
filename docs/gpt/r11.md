## 二、P1 问题

### P1：plan.js 文件读取路径双重拼接（可直接从源码推导的缺陷）

plan.js 先用 `absOf(intentPath)` 把输入转换成绝对路径，再交给 `readUtf()`；但 `readUtf()` 又无条件拼接 `ROOT + '/'`。无论 -Intent 传相对还是绝对路径，最终都被错误重复拼接根目录。plan 无法正常读取意图文件。

### P1：任务目录隔离了，但底层执行仍然不是并发安全的

**问题 A：run.ps1 会杀掉机器上所有 Java 进程。** fr_agent.ps1 的 compile/create 分支调用 run.ps1，而 run.ps1 开头 `Get-Process java | Stop-Process -Force` 并删 FineDB 锁文件。Agent 任务 A 编译时任务 B 启动编译可能直接杀掉 A 的 JVM；两个任务即使 runId 完全独立，也无法并发执行。r10 的"并发任务互不污染"只在文件命名层面成立，不在进程和运行环境层面成立。

**问题 B：模板修改链仍使用共享 staging。** template/patch_main.js 默认 `genv('TEMPLATE_STAGING', R + '/logs/template_staging')`，将 _pre.png/_post.png/manifest.json/修改后 CPT 写到共享目录；fr_agent.ps1 的 patch 分支没有传入当前 run 的 TEMPLATE_STAGING；modify_report.js 又从固定路径读 _post.png。竞态：A 修改生成 _post.png → B 覆盖 → A 的 modify_report 读到 B 的结果 → A 的 Artifact 混入 B 的预览和回归信息。

**建议**：runId 隔离必须贯穿整个执行链，目标结构 runs/{runId}/template/{source.orig.cpt, pre.png, post.png, manifest.json, output.cpt}。run.ps1 应拆分职责：普通执行器（不杀 Java、不删全局锁）+ 明确的环境恢复工具（操作者主动调用）。

### P1：原子写入实现本身有缺陷

_lib.js 现逻辑：先 `Files.delete(p)` 再 `ATOMIC_MOVE`——产生目标文件不存在的窗口；移动失败时原有效文件已被删除，降级 REPLACE_EXISTING 也不再原子。建议：临时文件与目标同目录 → 完整写入 → 直接 `ATOMIC_MOVE + REPLACE_EXISTING`（不预删）→ 明确处理不支持原子移动才降级 → 失败时清理临时文件保留原目标。另外 fr_agent.ps1 的 compile.json/patch.json 仍用 File.WriteAllText 直写，未统一原子写。

### P1：能力清单还不是真正的执行约束

- Manifest 只有 chart/condition/write/page 四组，未覆盖完整 ReportSpec、SQL 数据集、模板修改、语义查询等产品能力。
- Manifest 无独立 `regression` 状态（真实渲染成功 ≠ 持续回归验证）。
- plan.js 仍向 Planner 注入 `ReportSpec.capabilities()`，而非以 Manifest 的 agentAvailable 作为正式可用性约束——两套能力视图（ReportSpec.capabilities 决定校验/规划；CapabilityManifest 告诉 Agent 对外承诺）未建立统一的机器可验证关系。

建议五维：construction / serialization / rendering / **regression** / agentAvailable（由前四项+业务契约共同决定）。每项能力需机器可读证据引用（测试、载体、运行结果、证据版本），现在 evidence 主要是 README 文本，不能作为自动验收依据。

## 三、P2 问题

1. **RunId 严格身份校验**：`if (comp.runId && ...)` 只在存在但不匹配时拒；上游 JSON 缺 runId 仍放行。应 `if (String(comp.runId || '') !== String(runId)) reject`。PS 生成的 RunId 是秒级时间戳+四位随机，非严格唯一——建议 GUID，且 -RunId 限制字符集（字母数字下划线连字符）防路径穿越。
2. **plan 前置检查不分流**：无论什么意图都跑生产模型/Schema/关系证据 preflight，但 Planner 有 SQL 路与内嵌 rows 路两条——rows 路不一定需要数据库关系证据，却被关系证据问题阻断。应按意图数据集类型决定前置检查范围，补非 SQL 意图测试。
3. **文档历史接口残留**：docs/agent-demo-machine-daily.md 仍展示旧路径 logs/agent/*.json；旧演示未展示 plan → create → validate → preview 新方式。Agent 开发者照旧文档实现会直接违反新契约。

## 四、架构判断

项目主要矛盾已从「如何让 Java API 稳定构造成 CPT」变为「如何让 Agent 在复杂、并发、失败、重试的真实工作环境中可靠地完成一份报表」。两个子系统：A = FineReport 表达与执行引擎（ReportSpec/IR → Object/CPT/Runtime）；B = AI 报表创作平台（Agent/Semantic/Planner + Application/CapabilityManifest + ReportArtifact/Validation/Delivery）。通过稳定业务契约协作，Agent 层不应直接依赖 FineReport Java 类；不要为 Agent 便利把 Agent 状态/逻辑塞进 lib/ir.js 或 lib/object.js。不做批 K/L/M。

## 六、最终结论

r10 是重要架构进步，但未达其宣称的可靠性收口。优先解决三个基础问题：**任务隔离必须穿透进程、文件和 Runtime；能力声明必须成为真正的机器约束；Agent 必须能从计划到最终交付稳定完成整个任务**。解决后 fr-agent 才真正从强大的 FineReport 自动构造工具迈向可被现有 AI Agent 可靠使用的报表创作平台。
