## 1. 你的语义层已经不是简单的字段映射

我看了实际代码：

- `semantic/schema/inspector.js`：通过 JDBC `DatabaseMetaData` 获取真实表、字段、类型、主键、索引、外键。
- `semantic/schema/relation.js`：将结构约束、外键、命名推导关系分开，避免把猜测当成事实。
- `semantic/model/validator.js`：业务模型引用数据库字段时进行回溯验证，并检查关系基数。
- `semantic/model/evidence.js`：对数据侧唯一性证据做身份绑定、指纹验证和时效检查。
- `semantic/model/resolver.js`：业务术语解析为 resolved、ambiguous、unknown 三种状态。
- `semantic/query/sqlbuilder.js`：依据模型生成受控 SQL，而不是把自然语言直接翻译成 SQL。
- `semantic/planner/planner.js`：把结构化意图转换成 ReportSpec。

这已经形成了一个明确的语义处理链：

I2 · Schema

真实数据库结构

I3 · Model

业务实体、属性、指标、维度、关系

Resolver

业务术语解析与歧义识别

Preflight

模型回溯、关系证据和安全检查

I5 · SQL Builder

模型驱动的受控查询

I4 · Planner

结构化意图转换成 ReportSpec

这不是一个待建设模块，而是项目现有的重要资产。

真正需要研究的是：这条链在更复杂的真实业务场景中还有哪些能力边界，而不是重新建设它。

# 二、重新判断项目的真正方向

我认为项目的定位其实已经在 `docs/architecture/authoring.md` 和 `docs/agent-tools.md` 里面写得比较清楚：

Report Authoring，而不是 Report Generator。

这两个概念有很大区别。

Report Generator 解决的是：

> 给定一个结构化规格，生成 FineReport 模板。

Report Authoring 解决的是：

> 理解一个报表开发任务，判断需要做什么，操作 FineReport，验证结果，并交付完整成果。

而且你已经做了一个非常重要的架构选择：

不自己再造 Agent，使用现成 Agent。

这意味着 `fr-agent` 本身不负责运行大语言模型，也不需要自己建立一套完整的对话系统。

它应该提供的是一组足够专业、可靠、可组合的 FineReport 能力，让 Codex、Claude 或其他 Agent 可以真正承担报表工程师的工作。

因此，我现在认为项目的准确定位应该是：

# FineReport Report Authoring Engine

产品定位

为现有 AI Agent 提供完整的 FineReport 报表理解、创建、修改、执行、验证和交付能力。

外部 Agent： 理解自然语言、追问、决策、组织任务。

fr-agent： 提供 FineReport 专业知识、确定性操作、语义约束、引擎执行、质量验证和产物交付。

这个定位比我上一条说的“自主报表工程师”更准确，因为它明确了 Agent 与 `fr-agent` 的职责边界。

# 三、真正还缺少什么？

这次我不再列出已经存在的模块，而是从已有实现中找尚未闭合的地方。

## 1. 语义层需要验证通用性，而不是重新建设

目前我看到的语义模型是 `models/production/model.json`，围绕激光检测业务建立，具有实体、属性、指标、维度、关系和业务规则。

这说明语义层已经有真实业务模型作为载体。

但目前仍然有两个需要关注的地方。

第一，模型治理是否能脱离当前演示业务。

例如，一个新数据库接入后：

- 如何生成初始业务模型？
- 如何让 Agent 理解模型缺失？
- 如何补充业务指标定义？
- 如何处理模型版本变化？
- 数据库结构变化后如何发现模型失效？
- 如何维护关系确认和证据？

我认为未来值得建设的是模型的生命周期管理，而不是再增加一层语义抽象。

第二，目前代码中存在一个值得优先验证的术语归一问题。

在 `semantic/model/registry.js` 中，Resolver 候选主要使用 `target`、`ref`、`column` 等字段。

但是 `agent/tools/plan.js` 中的 `normalizeTerm()` 试图读取：

```
r.candidates[0].name
```

当前 Registry 构造的候选并没有统一提供这个 `name` 字段。

这意味着 SQL 意图中使用中文业务标签时，可能无法按预期归一为模型内部名称，随后在 Planner 的模型成员检查中被拒绝。

这不是架构缺失，而是已有语义链的一个实现契约问题。应该用中文标签、英文名称、物理列名分别跑端到端测试。

## 2. 报表规划能力与 IR 能力之间还有距离

这是我认为值得关注的重点。

你现在已经有：

- ReportSpec。
- IR。
- SpecCompiler。
- Planner。
- CapabilityManifest。

这几层的分工是合理的。

但目前 `ReportSpec` 的 SQL 编译路径主要是单 Sheet 表格、基础图表、派生比率公式等；底层 IR 已经具备更丰富的表达能力。

例如，IR 和对象图路线已经积累了：

- 条件属性。
- 参数控件。
- 图表。
- 超链。
- 子报表。
- 页面属性。
- 工具栏和部分填报结构。

这意味着目前存在一个重要的能力差：

FineReport 引擎能够做的事情，比 Agent 通过当前 ReportSpec/Planner 能够稳定完成的事情更多。

这恰恰是 `capability_manifest.js` 存在的价值。

所以我不建议简单地把所有 IR 功能暴露给 Agent，而应该逐步把真正成熟、可以组合验证的能力纳入 Authoring 接口。

这也是未来功能迭代的主要方向之一。

## 3. 模板修改能力是一个明显的产品短板

这里我看了 `template/inspector.js`、`template/locator.js`、`template/patch.js`、`template/diff.js` 和 `template/regression.js`。

目前已经具备：

- 读取现有 CPT。
- 获取 Sheet 和单元格范围。
- 读取单元格值。
- 检查数据集存在性。
- 替换单元格值。
- 替换已有数据集。
- 检查修改前后的结构差异。
- 执行、渲染和数据集回归。

这是一个很好的安全修改基础。

但当前白名单真正支持的修改操作主要只有：

| 修改操作    | 当前状态 |
| ------- | ---- |
| 替换单元格文本 | 已支持  |
| 替换单元格公式 | 已支持  |
| 替换已有数据集 | 已支持  |
| 修改样式    | 不支持  |
| 修改列宽、行高 | 不支持  |
| 增加、删除行列 | 不支持  |
| 修改筛选和参数 | 不支持  |
| 修改图表属性  | 不支持  |

这意味着现在的 Modify 更接近安全的局部内容修改器，还不是完整的模板编辑系统。

我认为这是未来必须逐步扩展的方向。

而且要坚持你现在的原则：先探针实证，再开放操作；不确定的操作就拒绝，不允许静默破坏原模板。

## 4. 验证系统需要从特定业务规则走向通用验收

这点我认为非常重要。

你已经有相当完整的验证基础：

- RunResult 阶段状态。
- 引擎执行。
- CPT 读回。
- PNG/PDF 渲染。
- 栅格数据检查。
- 外部真值对拍。
- 模板修改前后差异。
- 像素级渲染回归。
- CapabilityManifest。

但我发现 `agent/tools/validate.js` 目前仍然包含比较明显的生产业务假设：

例如，它默认按计划数量、完成数量、完成率的顺序检查栅格，计算：

\\[ 完成率=\frac{完成数量}{计划数量}\times100 \\]

这适合当前激光检测示例，却不能作为通用报表验收逻辑。

未来应该让验收规则来自任务本身。

例如：

```
AcceptanceSpec
  ├── execution
  ├── rendering
  ├── dataset
  │   ├── expectedColumns
  │   ├── expectedRows
  │   └── expectedValues
  ├── metrics
  │   ├── formula
  │   └── tolerance
  ├── layout
  ├── interactions
  └── regression
```

这里不是建议你照着再写一套新系统，而是建议把现有 `validate`、`TemplateRegression` 和 `ReportArtifact` 的验收契约逐步统一。

否则项目未来会出现一个问题：生成器越来越通用，验收器却仍然依赖某一个具体业务。

## 5. 现有 Agent 与 fr-agent 的协作闭环

这是我认为产品层面尚未完全闭合的地方。

现在的 `agent/tools/` 已经提供：

- discover
- resolve
- plan
- plan2spec
- compile/create
- validate
- preview
- patch/modify

接口已经相当清晰。

但要注意：`plan` 接收的是结构化意图 JSON，并不是自然语言本身。

这符合你选择现成 Agent 的设计，并不是错误。

真正需要证明的是：外部 Agent 能否稳定地使用这套接口完成复杂任务，而不需要用户或开发者不断手动拼接中间 JSON、修正文件路径、人工判断工具调用顺序。

换句话说，接下来应该重点验证：

一个现成 Agent 能否仅依靠 discover、resolve、plan、create、validate、preview、modify 这些工具完成真实任务？

如果这条链还需要开发者大量手动介入，那么工具接口虽然存在，产品闭环仍未完成。

## 6. Runtime：正在解决的问题不应该再被重复列成未来模块

R12 的方向我认可：

- FineReport Runtime 串行执行。
- 任务独立 RunId。
- 运行产物隔离。

这些属于你正在推进的 R12 正确性工作，不应当被我重新包装成一个未来才开始建设的模块。

# 五、最终目的：不是覆盖所有 FineReport API

我觉得这里还需要纠正一个可能影响项目发展的方向。

你花了很多时间研究 FineReport 的类、方法、对象结构、图表 API、参数控件和各种序列化细节。

这些工作有价值，但最终不应该以“把 FineReport 所有 API 都封装一遍”为目标。

原因很简单：

FineReport 的 API 数量非常大，而且有些能力只在 Web 端生效，有些依赖插件，有些只能通过实际渲染才能证明，有些 API 虽然存在却无法稳定组合。

如果以 API 覆盖率为终点，项目可能永远做不完。

我认为更合理的目标是：

覆盖足够多的真实报表开发任务，而不是覆盖所有底层 API。

例如：

- 从数据库创建生产日报。
- 创建多维统计报表。
- 创建图表分析报表。
- 修改已有报表的数据集。
- 增加指标和计算逻辑。
- 修改现有报表的布局和样式。
- 增加参数筛选和钻取。
- 复制现有模板并进行业务定制。
- 验证修改没有破坏原有功能。

这些真实任务才决定需要支持哪些 API。

# 六、我建议把最终验收目标定成这样

我会把 `fr-agent` 的最终目标定义为：

> 任何一个具备工具调用能力的成熟 AI Agent，只要接入 fr-agent，就能够在用户授权的数据源和 FineReport 环境中，独立完成常见报表的创建、修改和验证任务。

用户只负责提出需求、提供必要的业务口径和验收结果。

而系统需要负责：

1. 理解当前数据库和业务模型。
2. 判断需求是否可实现。
3. 识别缺失信息并向用户澄清。
4. 规划报表结构和数据查询。
5. 创建或修改 FineReport 模板。
6. 调用真实引擎执行。
7. 验证数据、结构、渲染和回归。
8. 根据失败证据进行修复。
9. 交付模板、预览和验收报告。

最终成功标准不是“支持了 200 个 API”，而是：

## 最终产品验收

给 Agent 一个真实报表开发任务：

- 不需要开发者编写 JS 或 Java。
- 不需要用户手动编写 CPT 或 IR。
- 不需要用户手动拼 SQL。
- 不需要用户手动操作 FineReport 设计器完成常规任务。
- 不会因为一次失败破坏已有模板。
- 能够提供真实执行和验收证据。
- 遇到不支持的能力会明确说明，不会假装成功。

下一阶段应该以真实任务作为主线，让语义层、ReportSpec、IR、模板修改、Runtime 和验证体系共同工作。哪一层阻碍任务完成，就针对那一层迭代。
