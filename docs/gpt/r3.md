问题 1：SQLBuilder 对跨表字段没有拒绝保护
P0 · 优先修复
这是我最关注的问题。

当前 semantic/query/sqlbuilder.js：
var table = ent.table;


随后维度处理：
var col = String(d.column || '').split('.').pop();


最终生成：
'SELECT ' + selectBits.join(', ') +
' FROM ' + table


也就是说，它取的是当前实体的表作为 FROM，然后把维度映射里的表名前缀去掉。

GitHub+1

这在当前单表报表中没有问题。

但是模型中有：
{
  "name": "machine",
  "table": "laser_files",
  "column": "source_id"
}


而日报使用的实体是：
{
  "name": "InspectionRecord",
  "table": "laser_aaa"
}


如果用户要求按机台统计，当前 SQLBuilder 可能生成：
SELECT source_id
FROM laser_aaa
GROUP BY source_id


它没有执行 laser_aaa 和 laser_files 的 JOIN。

同样，fileCount 指标来自 laser_files，但当前 metricSelect() 的 COUNT(*) 没有使用指标定义里的表名。

GitHub+1

这不是未来才需要考虑的抽象问题，而是当前模型已经暴露出来的边界。

我的建议：在实现 JOIN 之前，必须增加跨表拒绝闸。

第一步：
实体主表 = laser_aaa

选中的维度/指标：
  bizDate → laser_aaa 允许
  stage   → laser_aaa 允许
  machine → laser_files 拒绝
  fileCount → laser_files 拒绝


返回：
{
  "code": "UNSUPPORTED_CROSS_TABLE",
  "path": "dataset.dimensions[0]",
  "message": "当前查询不支持跨实体表字段"
}


不能生成一个表面合法、结果却错误的报表。

之后再单独做 JOIN。
问题 2：SQL Planner 对未知模型成员的状态判定不够严格
P0 · 优先修复
看 semantic/planner/planner.js 的 SQL 分支。

它会检查：
dims.forEach(function (dn) {
  if (dn && !hasOwn(dset, dn))
    validationWarnings.push(...);
});


指标也类似。

但是后面的状态判断是：
var sqlErrs = ctx.validateSpec(sqlSpec);
var sqlStatus = (sqlErrs && sqlErrs.length)
  ? 'rejected'
  : 'ready';


这里的 SpecValidator 只检查维度、指标名是否是非空字符串，并不负责判断它们是否真的存在于模型中。

GitHub+1

因此：
intent:
  dimensions = ["ghostDimension"]
  metrics = ["ghostMetric"]


即使产生模型成员警告，也有可能被 Planner 返回为 ready。

真正编译时，SqlBuilder 才会发现 UNKNOWN_REF。

这破坏了 Planner 的一个重要职责：
不能让未解决的业务语义进入 ready 状态。

建议：
- 未知模型成员：rejected。
- 多个业务候选：ambiguous。
- 后端能力暂不支持：deferred 或明确拒绝。
- 只有模型引用正确、Spec 合法、能力可用，才返回 ready。
并且增加专门的 SQL Planner 负测试。

P1 · 建议补齐
当前 ModelValidator 能够将模型引用回溯到 Schema。

load(Paths.semantic('query/sqlbuilder.js'));

  model: modelObj,

});


我没有看到这里加载并调用：
ModelValidator.validate(model, schema)


也没有看到 Runner 在 SQL 生成前重新检查模型与当前 Schema 的一致性。

GitHub+1

这意味着：
- 离线测试可以证明模型在测试时是正确的；
- 但生产数据库结构发生变化后，生成器不一定及时发现模型已经过期。
建议正式执行前增加：
读取 model.json
       ↓
读取对应 schema.json
       ↓
ModelValidator.validate()
       ↓
模型引用全部有效
       ↓
SqlBuilder.build()


这样 Schema Inspector 才真正成为生成链路的上游依赖，而不是一个独立工具。

P1

最终评价
我对这轮进展的评价比上次高不少。

之前我们讨论的是：
怎样让 fr-agent 有能力接受自然语言并生成 CPT？

现在已经有了一个真实样例证明：外部 Agent 可以根据自然语言需求、业务模型和工具接口，生成语义 ReportSpec，经过 SQL Builder 和 FineReport 后端，最终产出真实报表。

这已经跨过了从“报表生成工具”到“AI 报表创作引擎”的关键门槛。

但我不会因此认为它已经具备通用企业报表创作能力。

当前最大的限制不是缺少本体论、缺少 Agent 框架，也不是缺少 FineReport API。

而是：
1. 业务模型和 SQL 生成之间的正确性约束还不够严密。
2. 多实体关系尚未转化为可靠的 JOIN 规划。
3. 真实领域覆盖仍然只有一个主要样本。
4. 已有 CPT 修改还是一条完全独立的技术路线。
我的建议很明确：下一轮先不要做新功能。先做 I5.1，把上面几个 SQL 和 Planner 的问题修完。

这样才值得继续向多表 JOIN、图表和复杂报表迈进。

本次结论来自当前公开源码的静态检查和仓库内测试资产审查；我没有在你的 Windows + Nashorn + FineReport 环境重新执行整套测试，因此没有把仓库记录的运行结果冒充为我本轮亲自复测的结果。
