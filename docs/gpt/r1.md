结合这次重新检查的 main 分支源码，以及我们前面关于产品定位、ABR-1、IR/CPT、ANTLR 和现成 Agent 的讨论，我认为 fr-agent 已经到了一个需要改变优化重点的阶段：
前期重点是考古 FineReport、验证 API、建立对象构建能力；接下来重点应该转向稳定 IR、可靠生成、真实验收，以及让现成 Agent 能够安全地使用这些能力。
我不建议推倒重来，也不建议现在增加一套大型架构。
下面是我会给这个项目制定的实际改进计划。
一、先明确整体判断
我认为目前有五个需要分别处理的问题。
领域	当前状态	下一步方向
FineReport 对象构建	已经积累了大量真实 API 经验	稳定后端，减少回归
IR	能力越来越丰富，但约束还不够完整	建立稳定的 IR Contract
CPT	原生对象图导出与旧字符串生成并存	明确两条路径的职责
验证体系	有结构、渲染、回环和数据验证	建立分层验收和失败门禁
Agent 创作	尚未形成完整的自主创作闭环	让现成 Agent 使用 IR 和工具
我的优先级是：
稳定性优先
1. 修复现有确定性问题，避免错误产物进入部署。
2. 完善 IR 的结构校验、语义校验和能力边界。
3. 明确对象后端和 CPT 校验器的职责。
4. 建立 Agent 能够可靠使用的报表定义接口。
5. 完成一张真实业务报表的自主创作闭环。
下面具体展开。
二、第一阶段：先修复现有代码问题
这一阶段不增加新架构，只处理目前源码中已经能确认的问题。
P0：修复 IR 校验器
这是我认为最应该先做的事情。
当前 ir.js 的 validate() 已经覆盖很多内容，但它还不能可靠地处理任意不合法输入。
问题 1：缺少基础结构时，校验器自己可能崩溃
当前逻辑：
if (!IR.sheets || !IR.sheets.length) errs.push('no sheets');
IR.sheets.forEach(function (s, si) {
    if (!s.blocks || !s.blocks.length) {
        errs.push('sheet' + si + ': no blocks');
    }
    var types = s.blocks.map(function (b) {
        return b.type;
    });
});

如果 IR.sheets 不存在，记录错误之后仍然执行 forEach()。
如果 s.blocks 不存在，也仍然执行 map()。
这违反了验证器最重要的职责：输入错误时返回可读诊断，而不是自己抛异常。
GitHub+1
建议将校验拆成两个阶段：
validate(IR)
    │
    ├── validateRoot()
    │     ├── IR 类型
    │     ├── sheets 是否为数组
    │     └── datasets 是否为数组
    │
    ├── validateStructure()
    │     ├── sheet
    │     ├── blocks
    │     ├── block 类型
    │     └── 必需字段
    │
    └── validateSemantics()
          ├── 数据集引用
          ├── 字段引用
          ├── 参数引用
          ├── 图表引用
          └── 条件属性

第一阶段失败时，不执行依赖其结构的第二阶段。
问题 2：detail.link 校验不可达
当前代码先执行：
if (b.type !== 'chart') return;

后面又检查：
if (b.type === 'detail' && b.link) {
    // ...
}

这段 detail 校验实际上永远不会执行。
GitHub
建议直接把 chart、detail、cells 分别处理，不要把不同块类型的校验塞在一个分支里。
问题 3：条件属性的校验还不够严格
现在 checkConditions() 主要检查：
- 是否有 when。
- 是否有 formula、column 或 list。
- op 是否合法。
- then 是否非空。
但还有一些问题：
- formula、column、list 是否必须恰好选择一种？
- list 中的子条件是否递归合法？
- column 条件是否真的引用了数据集字段？
- value 是否符合 valueType？
- then 中的 bg、color、sizePt 是否是合法类型？
- 是否存在后端不支持的 action？
这些都应该成为 IR 校验的一部分。
GitHub+1
问题 4：缺少跨对象引用校验
这是 Agent 生成 IR 后最容易出错的地方。
我建议增加：
引用关系	校验内容
Detail → Dataset	数据集是否存在
Detail → Column	字段是否存在
Chart → Dataset	图表数据集是否存在
Chart → Category	分类字段是否存在
Chart → Values	数值字段是否存在
Cell → Dataset	数据集是否存在
Cell → Column	数据字段是否存在
Parameter Filter → Widget	参数控件是否存在
Parameter Filter → Dataset	过滤字段是否存在
Link → Reportlet	目标报表是否符合路径规则
这比单纯检查 JSON 格式重要得多。
我的建议：先把 validate() 做成一个真正可靠的语义校验器，不急着引入 JSON Schema、ANTLR 或其他解析框架。
P0：修复 Runner 的失败门禁
这里我发现了比单纯校验更重要的问题。
当前 make_api.js：
var irErrs = Ir.validate(IR);
check('IR VALIDATE', irErrs.length === 0);
if (irErrs.length) {
    irErrs.forEach(function (e) {
        stamp('IR ISSUE: ' + e);
    });
}
built = Obj.build(IR);

校验失败后仍然继续构建。
GitHub
另外，CPT 校验失败虽然会增加 FAILS，但后面仍然继续执行、导出和部署。
更值得注意的是，当前部署失败的 catch 只记录日志，没有增加 FAILS：
try {
    var osT = new J('java.io.FileOutputStream')(...);
    wb.export(osT);
    osT.close();
} catch (e) {
    stamp('CPT DEPLOY FAIL: ' + e);
}

这意味着部署失败存在最终退出码仍然为 0 的可能。
GitHub
我建议把管线明确划分为几个门禁：
输入加载
   ↓
IR 结构校验
   ↓ PASS
IR 语义校验
   ↓ PASS
对象构建
   ↓ PASS
CPT 导出
   ↓ PASS
CPT 结构验证
   ↓ PASS
FineReport 执行
   ↓ PASS
PNG/PDF 导出
   ↓
结果验收
   ↓
部署

每一阶段应该有自己的状态。
例如：
{
  "success": false,
  "stages": {
    "ir_validation": "passed",
    "object_build": "passed",
    "cpt_export": "passed",
    "cpt_validation": "passed",
    "execution": "failed",
    "deployment": "skipped"
  },
  "diagnostics": []
}

这只是响应格式示意。
有一点要特别说明：BR_SKIP_EXEC 是你已经设计的生产构建通道，不应该强制所有任务都必须执行和渲染。应该把验证等级明确区分为：
- 仅构建。
- 构建 + CPT 验证。
- 完整执行 + 渲染。
- 完整执行 + 业务数据核验。
这样不会破坏现有生产构建流程。
P1：修复参数面板的执行参数映射
这是一个比较具体、容易忽略的问题。
当前 object.js 已经支持：
- editor
- date
- combo
- number
- textarea
- radio
- checkbox
- combocheck
- treecombo
但 make_api.js 构造 wb.execute() 的参数时，只处理：
if (w.kind === 'editor' && w.value != null && w.value !== '') {
    pmap.put(w.name, String(w.value));
}

这意味着其他控件的默认值没有进入当前执行验证参数。
GitHub+1
建议建立统一的参数转换函数：
IR.param.widgets
       ↓
ParameterValueMapper
       ↓
HashMap
       ↓
wb.execute()

不同控件需要不同类型的转换，例如日期、数值、多选值和公式默认值。
不要简单地全部 String()。
这样才能保证你验证的报表和用户实际在参数面板里操作的报表一致。
P1：修复路径单点的剩余问题
make_api.js 仍然有：
var localCpt = 'D:/fineagent/demo_api.cpt';

但是 Paths.root 已经支持 FR_AGENT_HOME。
GitHub+1
建议确认这个路径是否是刻意固定的基线文件。
如果是，明确标记为固定基线位置；如果不是，应该统一通过 Paths 管理。
我不会要求为了消除一个硬编码就改变既有默认产物路径。默认路径和 MD5 基线必须保持兼容。
三、第二阶段：真正稳定 IR
这是接下来最重要的中期工作。
我认为你现在的 ir.js 有一个很好的基础，但有一个长期风险：
IR 正在不断增加功能，却还没有明确成为一个稳定的、供 Agent 使用的正式接口。
现在存在两条输入路径：
传统 Spec
   ↓
Ir.compile()
   ↓
ReportIR

以及：
Spec.IR
   ↓
ReportIR 直通

第二条路径很有价值。官方复杂模板的结构本来就不一定适合通过简单的 Spec 编译出来。
但是要让 AI 使用，就需要明确约束。
1. 增加 IR 版本
建议：
{
  "irVersion": "1",
  "sheets": [],
  "datasets": []
}

未来 IR 结构变化时，有明确的兼容依据。
不需要马上做复杂的版本迁移框架，但至少应当做到：
- 能识别当前版本。
- 不认识的版本拒绝构建。
- 明确哪些字段是必需的。
- 明确哪些能力不支持。
2. 区分三个层次
我建议你明确：
概念	作用
ReportSpec	人或 Agent 描述报表需求
ReportIR	经过规范化的报表结构
FineReport WorkBook	FineReport 原生对象图
例如：
用户需求
   ↓
Agent
   ↓
ReportSpec
   ↓
Ir.compile()
   ↓
ReportIR
   ↓
Ir.validate()
   ↓
Obj.build()
   ↓
WorkBook
   ↓
wb.export()
   ↓
CPT

复杂模板可以继续走 ReportIR 直通，不需要强行经过简化 Spec。
但我建议 compile() 不要直接修改输入对象。
当前 spec.IR 路径调用 extrasOut()，会向原始 IR 添加属性。
GitHub+1
最好让编译过程具备明确的纯度约定：
- 输入不被意外修改。
- 同一输入多次编译结果一致。
- 不依赖前一次调用残留状态。
这对 Agent 反复尝试修改报表尤其重要。
3. 建立明确的能力清单
不要一开始建设复杂的 Capability Registry。
先维护一份机器和人都能读的能力清单就够了。
例如：
能力	状态
单 Sheet 普通报表	已支持
单 Sheet 自定义单元格	已支持
参数面板	已支持部分控件
条件属性	已支持部分类型
常见图表	已支持部分类型
VanChart	已支持部分类型
浮动元素	已支持部分类型
多 Sheet	暂不支持
任意 CPT 反向转 IR	暂不支持
这里有一个明确的源码事实：
ir.js 的数据结构允许多个 Sheet，但 object.js 在第二个 Sheet 时直接抛出异常。
GitHub+1
我的建议不是马上实现多 Sheet，而是让 validate() 提前拒绝多 Sheet，并返回：
UNSUPPORTED_CAPABILITY: multi_sheet

这样 Agent 就不会误以为结构能表达就代表后端能生成。
四、第三阶段：重新明确 object.js 和 cpt.js 的关系
这是我觉得你需要在架构上明确的一件事。
目前有两条路径：
v2：字符串构建路径
Spec
cpt.js
XML 字符串
v3：原生对象图路径
ReportIR
object.js
WorkBook → wb.export() → CPT
我建议：
v3 是正式生成后端，v2 保留为回归对照和历史兼容路径。
但这里有个需要纠正的认知：
cpt.js 现在不只是一个字符串生成器，它还承担旧产物的校验和回环断言。
因此不要简单删除它。
我建议逐渐把职责区分清楚：
- v2 Builder：历史 XML 字符串生成。
- Legacy Validator：验证 v2 产物。
- Artifact Validator：未来验证 v3 产物的通用结构。
不一定需要马上拆文件，但代码职责要明确。
还有一个需要重点处理的细节：字体单位
我看到当前 object.js 的字体转换是：
var FR_SIZE = Math.round((sizePt || FONT_SIZE_PT) * 8);

而 cpt.js 的旧字符串路径使用：
var SIZE_BODY = 21;

这两个转换路径显然不是同一个数字口径。
GitHub+1
我不认为应该直接把其中一个改成另一个，因为两条路径使用的 API 和序列化机制不同。
但是现在 sizePt 这个名字容易造成误解：它实际上还涉及设计器显示字号与底层序列化单位之间的转换。
建议：
1. 将设计器字号、物理纸面字号、FRFont 内部单位明确区分。
2. 为 v2 和 v3 分别建立单位转换函数。
3. 建立 9、10.5、12、14、18、24 等字号的标尺测试。
4. 同时检查设计器显示值、CPT 属性值、实际 PNG 像素和物理尺寸。
5. 保留生产基线，不要为了统一数字而破坏现有渲染结果。
这是值得整理的知识，不应该继续依赖注释记忆。
五、第四阶段：提高 FineReport 后端的可靠性
我认为 object.js 已经积累了相当多真实 API 知识，现在不应该盲目追求功能数量。
应该优先减少潜在的数据错误和隐式行为。
1. 完善数据类型映射
当前嵌入式数据集：
var jType = c.type === 'number'
    ? Class.forName('java.lang.Integer')
    : (c.type === 'float'
        ? Class.forName('java.lang.Double')
        : Class.forName('java.lang.String'));

对应的值转换也是：
- number → Integer
- float → Double
- 其他 → String
GitHub
这个设计对当前演示数据足够，但未来面对真实业务数据时会有局限：
- 大整数可能超出 Integer 范围。
- 金额和高精度小数可能需要 BigDecimal。
- 日期、时间不能全部当作字符串。
- 布尔类型需要明确转换。
- 空值需要保留语义。
建议建立明确的数据类型映射：
IR 类型	Java 类型建议
string	String
integer	Integer 或 Long
decimal	BigDecimal
float	Double
boolean	Boolean
date	Date/对应日期类型
datetime	Timestamp/对应日期时间类型
这需要按 FineReport 实际支持情况逐一验证，不要一次性全部实现。
我会优先补 decimal 和 long。
2. 消除后端静默失败
例如当前 object.js 有一些这样的代码：
try {
    dsc.setColumn(...);
} catch (eCol) {
}

以及某些控件属性设置失败时直接吞异常。
GitHub+1
我理解这些写法可能是为了兼容不同 FineReport 对象实现。
但如果一个关键属性设置失败，生成器应该知道。
建议区分：
- 必须成功的属性：失败就抛错。
- 可选增强属性：允许失败，但返回 warning。
- 兼容性探测属性：记录实际使用的能力分支。
不要让后端悄悄忽略一个用户明确要求的属性。
3. 把样式缓存与对象生命周期明确化
当前样式缓存：
var styled = {};
function stOf(stSpec) {
    var k = JSON.stringify(stSpec);
    if (!styled[k]) {
        styled[k] = style(stSpec);
    }
    return styled[k];
}

这个设计很好，能够让相同样式复用同一个对象。
GitHub
但是 FineReport 的部分对象存在共享实例问题，你已经遇到过字体颜色污染。
因此建议建立专门的回归用例：
- 两个单元格使用相同样式。
- 两个单元格使用不同字体颜色。
- 条件属性改变字体颜色。
- 不同 Sheet 使用相同样式。
- 导出后重新读取。
核心要求是：样式复用不能导致跨单元格意外污染。
4. 限制 Agent 能够生成的危险输入
这项工作应在 Agent 正式接入之前完成。
我看到了三个具体入口：
- nav 控件将 w.url 拼接进 JavaScript。
- toolbar 允许使用 className 指定 Java 类。
- floats.imageFile 直接读取本机文件路径。
GitHub+2
这些接口对本地可信 Spec 很灵活，但不能直接把未来 Agent 的输入当成可信代码。
建议：
输入	约束
toolbar className	只允许本地注册的类
nav URL	严格校验 URL 和允许协议
iframe URL	设置域名白名单或本地资源策略
imageFile	限制在指定资源目录
SQL	只允许明确授权的数据源和只读查询
数据库凭据	不进入 Agent 可见的 Spec 或 IR
特别是数据库凭据：当前 Runner 的连接注册需要 driver、URL、user、password。未来应该通过本机受信任配置或凭据引用来提供，Agent 只选择连接名称，不直接接触凭据。
GitHub+1
这既是安全边界，也是产品设计边界。
六、第五阶段：把验证体系做成真正的产品能力
这是我认为 fr-agent 最值得继续投资的地方。
你已经积累了很多 FineReport 官方模板、渲染结果、像素对比、数据真值和探针。
这批积累不能仅仅留在 README 和历史日志中。
建议逐步形成一个分层验证体系：
验证类型	验证目标	主要手段
Unit	IR 结构和映射	JS 测试
Serialization	CPT 是否符合结构要求	XML 解析和结构断言
Roundtrip	FineReport 读写是否保留关键属性	引擎读回
Execution	SQL、公式、参数是否正常	wb.execute()
Data	数值是否正确	结果栅格与真值对比
Rendering	页面是否符合设计	PNG/PDF
Regression	修改是否破坏历史能力	固定样本回归
这里我有一个特别重要的建议：
不要让所有测试都依赖完整 FineReport 环境。
可以把测试分成两类：
- 不依赖 FineReport 的快速测试：IR 校验、输入规范、引用关系、确定性转换。
- 依赖 FineReport 的集成测试：对象构建、CPT 序列化、执行和渲染。
这样每次修改 ir.js 都可以快速发现大量问题，不必每次启动完整引擎。
官方 240 份模板应该怎么利用？
我建议不要把 240 份模板都当作重建目标。
它们最有价值的用途是建立能力覆盖证据：
- 哪些对象族使用频率最高？
- 哪些对象组合最常见？
- 哪些能力已经能稳定构建？
- 哪些能力只能读取，尚不能构建？
- 哪些能力已经经过真实渲染验证？
例如，条件属性、参数面板、图表、数据字典、HTML 显示、富文本、浮动元素等，可以逐步形成独立的能力样本。
你已经有一部分普查数据，这个工作应该继续，但不必继续扩大成无止境的考古工程。
下一步应该从“发现更多 FineReport 特性”转向“证明已经支持的特性可以稳定组合使用”。
七、第六阶段：开始 AI 报表创作，但不要急着上 MCP
回到我们最初确定的产品目标：
用户提出需求，Agent 自主完成报表，用户负责验收。
我认为现在已经可以开始为这个目标做准备了。
但是我建议先不要开发 MCP Server。
先设计一个 Agent 能够稳定使用的创作流程：

现成 Agent
       ↓
探索数据源与能力
       ↓
生成 ReportSpec / ReportIR
       ↓
调用现有 Runner
       ↓
IR 校验
       ↓
FineReport 对象构建
       ↓
CPT 生成
       ↓
真实运行
       ↓
PNG/PDF + 数据结果
       ↓

       ↓
交付用户

第一版 Agent 应该能完成什么？
我建议不要做一个过于复杂的场景。
先选择一种典型业务报表，例如：
生产日报：按车间展示计划数量、完成数量、完成率，并支持日期和车间筛选。
这个场景可以同时验证：
- SQL 数据集。
- 多个字段。
- 数值类型。
- 参数面板。
- 参数过滤。
- 汇总公式。
- 样式。
- 执行结果。
- PNG/PDF 渲染。
而且它不需要先实现 CPT 反向解析。
第一版的 Agent 不必直接编写 FineReport Java API，也不应该生成任意 Nashorn 代码。
它只需要输出受约束的报表定义。
Agent 的工作指南
第一版只需要一份短小的 SKILL.md 或 Agent Instructions：
1. 先探索数据源和字段。
2. 不允许猜测字段名。
3. 检查当前后端支持的报表能力。
4. 根据用户需求生成 ReportSpec/ReportIR。
5. 先执行校验。
6. 调用生成和验证流程。
7. 根据诊断修复。
8. 最终交付 CPT、预览图和验证摘要。
9. 未经过真实验证，不得声称报表已经可用。
这样就可以验证产品方向，不需要自己开发 Agent。
八、已有 CPT 修改应该什么时候做？
这是你未来很重要的一项能力，但我不建议现在立刻建设通用 CPT → IR 转换器。
原因是：
FineReport 能读取 240 份官方 CPT，并不等于你已经能把这些对象图完整映射成通用 ReportIR。
我建议按三个小步骤来做：
第一步：读取已有 CPT。
通过 FineReport 原生 API 得到 WorkBook 对象。
第二步：提取有限的结构。
先只支持一类报表，例如：
- 单 Sheet。
- 普通明细表。
- 常见样式。
- 常见数据集。
- 常见参数。
第三步：修改后重新导出并对比。
验证：
- 未修改的单元格是否保留。
- 样式是否保留。
- 公式是否保留。
- 数据集和参数是否保留。
- 原有渲染是否发生意外变化。
我甚至建议第一版不必强求把所有内容转换成完整 IR。
可以先做一种有限的 Template Patch：
已有 CPT
   ↓
FineReport WorkBook
   ↓
定位目标对象
   ↓
局部修改
   ↓
重新导出
   ↓
差异验证

这可能比完整 CPT → IR 转换更容易实现。
当然，前提是 FineReport 的对象图 API 能够可靠保留未修改部分。
ANTLR 仍然没有必要。
九、我会怎么安排接下来四个迭代？
这是我最终建议的执行顺序。
迭代 1：可靠性修复
最高优先级
- 修复 Ir.validate() 的异常路径。
- 修复 detail.link 不可达校验。
- 补数据集和字段引用检查。
- IR 校验失败立即停止构建。
- 部署失败正确反映到退出码。
- 修复参数面板默认值映射。
- 处理路径硬编码。
  
  验收：非法 IR 能返回诊断，不产生或部署无效报表。

迭代 2：IR 稳定化
- 定义 ReportIR 版本。
- 明确支持的 block、widget、chart 类型。
- 明确单 Sheet 等暂不支持能力。
- 建立结构和语义校验。
- 统一数据类型定义。
- 确保编译不意外修改输入。
  
  验收：固定样本的 IR 校验稳定，已有产物回归不变。

迭代 3：端到端业务验证
- 选择一张真实业务报表。
- 形成完整 ReportSpec/IR。
- 验证数据、参数、样式和图表。
- 输出 CPT、PNG、PDF。
- 建立业务数据真值核对。
  
  验收：一张真实报表可以重复生成、执行、验证。

迭代 4：现成 Agent 接入
- 写 Agent Instructions。
- 提供稳定机器调用入口。
- 接入 Codex 或 Claude Code 中的一个。
- Agent 自主探索、生成、修复、验证。
- 根据实际体验决定是否增加 MCP。
  
  验收：Agent 能够独立完成一次真实报表创作任务。

暂缓事项	原因

十一、我认为 fr-agent 最终应该形成什么样的技术资产？
不是越来越多的 Java API 封装，也不是越来越复杂的编译器。
我认为最终最有价值的是这四项：
1. ReportIR
AI 可以理解和生成的报表结构模型。明确、可校验、有版本。

2. FineReport Backend
把 ReportIR 可靠地转换成 FineReport 原生对象图，并输出 CPT。

3. Verification Engine
能够验证结构、执行、数据、渲染，并返回机器可理解的诊断。

4. Agent Interface
让现成 Agent 能够探索、创建、修改和验证报表，而不必理解 FineReport 内部实现。

这四项才是 fr-agent 的核心资产。
最终建议：我会先让你做这五项
如果把上面所有内容压缩成下一轮实际开发任务，我会给出这个顺序：
顺序	任务	是否立即做
1	修复 IR 校验器和 Runner 失败门禁	立即
2	完善 IR 的跨对象引用和能力边界	立即
3	处理参数默认值、数据类型和 Agent 输入约束	紧接着
4	建立一张真实业务报表的完整生成验证样本	下一阶段
5	接入一个现成 Agent，验证自主创作	随后
我的核心判断是：fr-agent 现在不缺更多 FineReport API 研究，也不缺新的架构概念，真正缺的是把现有能力变成一个可靠、可组合、可被 AI 使用的创作接口。
我会特别坚持两条原则：
- 现有真实 FineReport 验证过的代码，不轻易重写。
- 每增加一项能力，都必须有对应的 IR 校验、对象构建测试和真实结果验证。
这样才能让项目从一个技术上很有意思的 FineReport 生成器，真正走向一个能够让 AI 自主完成报表工作的工具。
如果让我现在开始动手，我会先处理迭代 1：可靠性修复，不增加新目录、不引入新框架，先把当前管线的错误处理和 IR 校验做扎实。  认可就执行。
