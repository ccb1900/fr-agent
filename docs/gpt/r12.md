# r12.md — 执行模型修正：单实例 Runtime Supervisor + 多任务队列（r11 的补充，冲突以 r12 为准）

> 来源：外部审查对 r11 的修正。审查者承认 r11 把「任务隔离」与「并发执行」混为一谈。
> 基准：main/2b2a3af 之上（r11 执行中）。本文与 r11 偶有冲突时，**以本文为准**。

## 一、核心修正：并发提交 ≠ 并发执行

FineReport 环境不支持多 Runtime 实例同时运行；要求两个 FineReport 任务真正并行会引入引擎级冲突，反而破坏可靠性。正确架构：

**任务可以并发提交、独立排队、独立追踪，但 FineReport Runtime 必须串行执行。**

```
Agent 任务层：允许并发
  Task A (runId-A) ┐
  Task B (runId-B) ┘ 独立任务目录、独立状态、独立结果
        ↓
Runtime 执行队列：串行
  Task A · Running  /  Task B · Queued
  全局单执行权，任何时刻最多一个 FineReport Runtime 任务
        ↓
FineReport Runtime：单实例、串行执行、受控生命周期
```

**即使使用两个不同 RunId，也不能绕过 Runtime 的全局执行锁。**

## 二、任务隔离仍然必须（修复方式=每任务独立工作目录，不是多实例并行）

r11 指出的 staging 串扰问题成立，只是解法是让每个任务拥有自己的工作目录：

```text
logs/agent/
  runs/{runId-A}/  compile.json artifact.json template/{pre.png,post.png,manifest.json}
  runs/{runId-B}/  compile.json artifact.json template/{pre.png,post.png,manifest.json}
  runtime/
    queue/         排队任务描述（runId + verb + 参数 + submittedAt）
    current.json   当前执行权持有者（runId + pid + startedAt）
    lock/          全局单执行权互斥（目录即锁，跨进程原子）
```

同时满足：Agent 可同时提交多任务；每任务独立输入/日志/产物/验收；Runtime 只执行队列中的一个；任务失败不覆盖其他任务结果；同一任务可追踪、恢复、审计。

## 三、run.ps1 的处理（修正 r11 表述）

`Get-Process java | Stop-Process` 与删 FineDB 锁**不能简单理解为错误**——若用于清理上一次异常退出遗留的 FineReport 环境状态，在受控单实例模型下有存在理由。

**真正的问题**：它们现在是每次执行的默认前置动作，而不是**有条件的 Runtime 生命周期管理**。

拆分职责：

| 模块 | 职责 |
| --- | --- |
| TaskQueue | 接收并排队任务 |
| RuntimeLock | 保证全局单任务执行 |
| RuntimeSupervisor | 管理 FineReport JVM 生命周期 |
| Recovery | 异常退出后的受控恢复 |
| RunExecutor | 执行具体的 compile / patch |
| ArtifactStore | 保存任务独立产物 |

**尤其不能让普通任务启动时随意杀掉正在工作的 JVM。恢复操作必须先确认当前 Runtime 已经失效，再处理遗留锁。**

## 四、r11 验收标准修订

原「两个任务并发运行，互不污染」→ 改为 **「两个任务并发提交，Runtime 串行执行，任务状态和产物完全隔离」**。

新增集成测试（覆盖 PowerShell、Nashorn、Application、FineReport Runtime 全链，JS 单测不可替代）：

1. A、B 同时提交，A 执行、B 排队。
2. A 执行成功后，B 自动开始。
3. A 执行失败，B 仍能执行。
4. A 执行过程中重复提交 B，不产生第二个 Runtime。
5. Runtime 异常退出，队列状态保持可恢复，不把未完成任务标记为成功。
6. A 的模板修改产物、预览和 manifest 不会被 B 覆盖。

## 五、结论

fr-agent 不需要多实例并行，而需要**单实例 Runtime Supervisor + 多任务队列**。这比简单的文件隔离更重要，应是 `application` 与 FineReport Runtime 之间的**正式基础设施**，而不是散落在 PowerShell 脚本中的互斥逻辑。

## 六、执行落点（本轮 r12）

- `agent/tools/runtime.ps1`：RuntimeSupervisor——acquire（自旋取锁，含陈旧持有者 Recovery 判定）/ release / status / recover。全局锁=`logs/agent/runtime/lock` 目录原子创建；current.json 记 runId+pid+startedAt；queue/ 记排队态。
- `agent/tools/fr_agent.ps1`：compile/create、patch/modify 两条**会起 Runtime** 的路径经 acquire→（-NoKill）run→release 包裹；零引擎 verb（discover/resolve/plan/plan2spec/validate/preview）不取锁。
- `run.ps1`：保留 `-NoKill`（agent 路径在 Supervisor 保证单实例下用 -NoKill，绝不误杀在跑的 JVM）；kill+删锁降格为 Recovery 专用动作（Supervisor 发现 current 持有者 pid 已死时才执行）。
- 产物隔离：runDir + per-run staging（r11-2 已落）纳入 Supervisor 视图。
- 集成测试：`verify/integration_runtime.ps1` 覆盖上述 6 场景。
- r11 其余项（manifest regression 维度、plan preflight 按数据集类型分流、文档更新）作为补充继续，冲突处以 r12 为准。
