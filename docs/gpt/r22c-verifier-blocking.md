### 3\. 复合键验证：发现一个 P1

这是本轮唯一需要阻断的地方。

`verify/verify_sql_data.js` 的复合键模式目前这样做：

* 将真值文件读入 `det`，以 `day@machine` 为键。

* 将生成结果读入 `gMach`，同样以 `day@machine` 为键。

* 遍历 `gMach`，检查对应真值是否存在以及三个指标是否一致。

* 检查总计行。

问题在于：它只遍历生成结果，没有反向检查真值中的所有记录是否都出现在生成结果里。

例如：

* 真值有 10 条日期 × 机台记录；

* 生成结果只有 9 条；

* 缺失的那条没有被遍历；

* 如果总计行仍然正确，验证器就可能通过。

另一个问题是：

```javascript
gMach[p[0] + '@' + p[1]] = ...
```

相同复合键重复出现时，后面的记录会覆盖前面的记录，没有重复键失败检查。

真值侧的 `det` 也存在同样的覆盖行为。

这意味着目前的验证器不能严格证明：

* 真值和生成结果具有完全相同的键集合；

* 每个日期 × 机台组合恰好出现一次。

这不是代码风格问题，而是数据验收可能假通过。

P1：开跑前必须修复

我建议只补以下逻辑：

* 真值侧和生成侧分别统计重复键，重复即失败；

* 比较双方完整键集合，不能只检查生成结果中的键；

* 比较明细行数；

* 保留现有 plan、done、rate 和 grand total 检查。

不需要引入新的验证框架。

### 二、`compare_paths.js` 的复合键实现

整体方向正确：

* `AGENT_GRID_KEYCOLS` 支持指定复合键；

* 增加 `keyDupsA/B`；

* 重复键会使 `equal=false`；

* 未设置环境变量时保留旧单键路径。

但有一个实现假设：

```javascript
for (var c = KEYC.length; c < n; c++)
```

这里默认键列是从第 0 列开始连续排列的。

对于当前明确使用的 `0,1` 没问题，但配置本身没有验证连续性。如果传入 `1,0` 或 `0,2`，键列识别与后续比较就可能不一致。

建议将配置限制为连续前缀列，例如 `0`、`0,1`，非法配置直接报错。不要为了支持任意列位置增加复杂逻辑。
