### 审查结论

### 1\. Mutex 内二次检查：通过静态审查

`agent/tools/fr_agent.ps1` 的改动符合上轮提出的修复方案：

* 入口处保留快速重复检查。

* `Invoke-UnderMutex` 取得 Mutex 后，先检查对应的引擎产物。

* 检查发生在 Runtime 哨兵登记和引擎执行之前。

* 已存在时返回 `dup = true`，调用方返回 `RUNID_EXISTS`。

* `compile` 传入 `compile.json`，`patch` 传入 `patch.json`。

* 由于产物组装仍在 Mutex 内，前一个调用释放 Mutex 时，产物已经写完，后一个调用可以检查到它。

因此，上轮描述的 A、B 两个进程都通过入口检查，随后依次进入 Mutex 并重复执行引擎的问题，在生产代码路径上已经被堵住。

没有新增锁、队列、Token 或 Supervisor。这一点是正确的。

### 2\. S24b：测试方向正确，但还不能证明竞态确实被命中

这里有一个值得认真处理的问题。

目前 S24b 的关键步骤是：

```powershell
$r24a = Start-Process ...
$r24b = Start-Process ...
```

然后等待两个进程完成，断言一个成功、一个 `RUNID_EXISTS`。

问题是：两个进程启动得很近，不等于它们一定都在第一个进程写入 `compile.json` 之前完成了入口检查。

例如：

* A 启动并通过入口检查。

* A 取得 Mutex，执行引擎，写入 `compile.json`。

* B 此时才真正执行到入口检查。

* B 直接在 Mutex 外发现 `compile.json`，返回 `RUNID_EXISTS`。

这个测试同样会通过，但它根本没有执行到新增的 Mutex 内二次检查。

也就是说，S24b 目前能够证明同 RunId 的两个调用最终只有一个成功，却不能确定新增的二次检查就是阻止第二次执行的原因。

建议只补强 S24b 的竞争条件，不改生产架构：

* 测试进程先取得与 Agent 相同的命名 Mutex。

* 确认目标 RunId 的 `compile.json` 尚不存在。

* 启动两个独立 Agent 进程，让它们在 Mutex 外完成入口检查并等待。

* 测试进程释放 Mutex。

* 断言一个成功、另一个 `RUNID_EXISTS`，并确认只有一次引擎执行。

这样才能稳定命中这次修复所针对的竞争窗口，而不是依赖进程调度碰巧发生。

另外，目前 S24b 只验证了 `compile`。`patch` 的调用代码也正确传入了 `patch.json`，但还没有对应的并发验收。至少应增加一项针对 patch 调用路径的检查，确认它没有漏传或传错检查文件。
