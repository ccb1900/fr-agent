一、初步审查结果：当前 Runtime 确实可以大幅收敛
我已经读取了最新提交中的 fr_agent.ps1、runtime.ps1、config.ps1、run.ps1、runraw.ps1、集成测试、Artifact 契约和架构文档。

先说结论：R14 的 Named Mutex 值得保留，但围绕它建立的状态管理体系明显偏重。

当前实际存在两套东西：
- 操作系统提供的 Named Mutex：负责真正的互斥。
- 项目自建的 queue、owner、done、history：负责登记、状态追踪和恢复。
第二套并不是实现互斥所必需的。尤其是当前 queue 并不是真正的调度队列：任务实际是直接竞争 Mutex，代码没有按照 submittedAt 调度执行。因此，文档中的队列排序和真实执行顺序不是一回事。

这正是可以收敛的地方。
二、当前代码中，真正需要处理的几个问题
以下是我从实际代码中确认的，不是推测。

P1 · 必须先处理
 1. Patch 的 Java 进程没有被记录
fr_agent.ps1 的 patch 流程设置了：
$env:FR_AGENT_JAVA_PIDFILE = "$runDir\java.pid"


但随后调用的是 runraw.ps1。

我检查了 runraw.ps1：它直接执行 Java，没有读取 FR_AGENT_JAVA_PIDFILE，也没有记录进程 PID 和启动时间。

这意味着：
- compile 路径会记录 Java 进程身份。
- patch 路径实际上没有记录。
- 如果 PowerShell 在 patch 执行期间异常退出，恢复机制可能找不到遗留 JVM。
- Do-Recover-Previous 即使没有成功终止 JVM，仍然会尝试删除 FineDB 的 db.lck。
这是当前最值得优先修复的问题。不能在没有确认 JVM 已经退出的情况下删除它的锁文件。

相关代码：
- fr_agent.ps1
- runraw.ps1
- runtime.ps1

P1 · 必须先处理
 2. Recovery 有绕过互斥的入口
runtime.ps1 对外暴露了 recover-previous，这个分支直接调用 Do-Recover-Previous，没有取得 Mutex。

而 Do-Recover-Previous 可以：
- 终止 Java 进程。
- 删除 FineDB 锁文件。
- 删除 owner.json。
- 将任务标记为 lost。
更值得注意的是，当前集成测试 S14 直接调用了这个入口。

这相当于我们一边用 Mutex 保证串行，一边又保留了一个可以绕过 Mutex 修改运行状态的入口。

建议彻底取消独立的 recover-previous 操作入口。恢复只能由持有执行权的主流程内部完成。

P1 · 必须先处理
 3. 损坏的 owner.json 并没有真正 fail-closed
fr_agent.ps1：
if (Test-Path $of) {
    try {
        $prev = Get-Content $of -Raw -Encoding UTF8 | ConvertFrom-Json
    } catch {
        $prev = $null
    }
}


随后只有 $prev 存在时才进行前任身份检查。

所以 owner.json 存在但解析失败时，当前流程可能直接继续执行，之后 mark-running 又会覆盖旧文件。

这与 docs/architecture/runtime-supervisor.md 宣称的损坏 Owner 必须 fail-closed 不一致。

S19 测试的是独立 recover 操作，不是损坏 Owner 时真正发起 compile 或 patch 的情况。

修复原则：不存在、合法、损坏、不可读取必须区分。未知状态不能自动覆盖。

P1 · 必须先处理
 4. 测试可能破坏真实运行状态
verify/integration_runtime.ps1 的 Reset-Rt 会清理：
logs/agent/runtime/owner.json
logs/agent/runtime/queue/*
logs/agent/runtime/done/*
logs/agent/runtime/history.log


这些就是正常运行使用的 Runtime 目录。

测试没有先取得生产 Mutex，也没有使用完全隔离的 Runtime 目录。

因此，测试和真实任务并发时，测试可能删除正在执行任务的状态记录。

这不是普通测试覆盖率问题，而是测试隔离问题。必须先解决。

P2 · 收敛时一起处理
问题	当前代码表现	处理方向
Try-CreateNew	所有异常都返回 false	只将文件已存在识别为重复，其余异常抛出
unregister	只凭 RunId 删除记录	删除这个外部操作入口
JVM 终止	检查 PID 后再 Stop-Process -Id	使用已经验证的 Process 对象操作，并等待退出
queue	只登记和展示等待状态	不再承担调度职责

另外还有两个值得纠正的设计认知。

第一，Mutex 不保证 FIFO。 当前队列按时间排序，只能说明展示顺序，不能说明实际执行顺序。没有明确的 FIFO 业务需求，就不应该自建调度器。

第二，当前 Mutex 名称没有 Global\ 前缀。 .NET 在 Windows 下默认使用当前登录 Session 的 Local 命名空间。如果所有调用都在同一个登录 Session 中运行，这没有问题；如果任务计划程序、服务和桌面进程可能跨 Session，就必须重新确定 Mutex 的作用域。

三、我建议的最终架构
不是再设计一套 Runtime Supervisor，而是缩减成一个单实例执行入口。
fr_agent.ps1

统一入口，区分纯工具与引擎操作

纯工具

discover / resolve / plan / validate / preview
不获取 Mutex


引擎操作

compile / patch
获取 Mutex




.NET Named Mutex

唯一互斥机制，超时后返回明确错误

.NET Process

启动 Java、记录进程身份、等待退出、检查退出码

FineReport

执行报表创建或修改


Artifact / RunResult

独立完成结果整理和验收，不继续占用 Mutex


这里有一个可以进一步缩短锁占用时间的地方：

当前 compile 在 Mutex 内执行完 FineReport 后，还会调用 application/create_report.js；patch 也会在锁内调用 application/modify_report.js。

我检查了这两个文件，它们负责读取 JSON、组装 Artifact、执行契约验收，并不需要再次初始化 FineReport 引擎。

因此可以把它们移到 Mutex 释放之后。
最终保留与删除清单
组件	最终决策	原因
Named Mutex	保留	Windows/.NET 成熟的跨进程互斥
Process	保留	.NET 标准进程管理
runtime.ps1	大幅简化	不再作为独立状态管理服务
queue/	删除	不需要自建任务调度
done/	删除	Artifact 已保存结果
owner.json	合并	如需自动恢复，仅保留一个最小活动任务记录
history.log	降级	仅供诊断，不参与正确性判定
OwnerToken	重新评估	同一进程内部持锁操作后，没有必要维持独立管理协议
recover-previous	删除	禁止绕过主执行入口
FIFO	不实现	当前没有必要

一个重要的取舍：自动恢复还是安全拒绝？
我不建议为了追求自动恢复，再创造一套复杂的进程恢复协议。

目标应该是：
1. 正常退出：清理当前任务状态，释放 Mutex。
2. PowerShell 异常退出：操作系统释放或放弃 Mutex。
3. 下一次取得 Mutex：检查遗留任务记录。
4. 能准确验证 Java 进程身份时，才允许针对该进程恢复。
5. 无法确认进程身份、进程状态或 FineDB 状态时，拒绝启动新任务，要求人工处理。
特别是 Process.Kill() 本身是异步的，调用后还要 WaitForExit() 确认进程退出。不能把调用 Kill 当作进程已经消失。

四、实际迁移顺序
我不建议一次性改掉全部 Runtime。按以下顺序，既能减少自研代码，也能避免破坏已经正常工作的报表生成链。
1. 第一步：修复当前安全缺陷
   - patch 进程身份记录补齐。
   - 损坏 Owner 拒绝继续执行。
   - 删除无 Mutex 保护的 Recovery 入口。
   - 未确认 JVM 退出前禁止删除 FineDB 锁。
   - 集成测试改为独立 Runtime 目录。
2. 第二步：简化 Runtime
   - 删除 register/unregister 队列协议。
   - 删除 done 状态目录。
   - 取消 FIFO 语义。
   - 将状态管理收敛到主执行流程内部。
   - 如保留自动恢复，只留一个最小 active 记录。
3. 第三步：统一 Java 启动方式
   - compile 和 patch 使用同一套进程启动与等待机制。
   - 统一记录 PID 和 StartTime。
   - 统一异常、退出码和日志处理。
   - 使用已验证的 Process 对象处理遗留进程。
4. 第四步：缩短 Mutex 持有范围
   
   只保护真正调用 FineReport 引擎的代码。Artifact 生成和纯 JS 验收放到锁外。
5. 第五步：重新验收
   - 两个不同 RunId 并发，证明不会同时进入引擎。
   - 相同 RunId 并发，证明不会污染同一个运行目录。
   - compile 和 patch 分别验证崩溃恢复。
   - 验证损坏状态、无法确认 PID、JVM 未退出等情况均拒绝危险恢复。
   - 验证测试不会清理生产 Runtime 状态。
五、这次审查的最终判断
保留 Mutex，重做薄 Runtime
不建议回滚 R14，也不建议继续完善现有 Supervisor。

当前架构中真正有价值的是：
- Named Mutex 的单实例互斥。
- Java 进程生命周期管理。
- FineReport 执行结果的可信验收。
其余很多状态协议可以删除或合并。

还有一个需要纠正的技术依据：当前代码注释称 TerminateProcess 释放 Mutex 时不会抛 AbandonedMutexException。但微软 .NET 文档明确描述，持有 Mutex 的线程终止后，下一位获得 Mutex 的线程会收到该异常，进程被突然终止也是文档举出的情形。这个说法必须在用户实际 Windows/.NET 环境做最小实验，不能直接当作架构事实。
