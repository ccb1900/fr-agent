## 一、R13 的总体评价



方向正确

仍有并发正确性缺口



这轮不是表面修补。特别是把 `runtimeState` 与 `businessResult` 分开、将任务年龄降为告警、引入 OwnerToken，以及处理死等待者，是正确的工程方向。

但我检查了当前 `runtime.ps1`，发现还有几个问题不能因为 S1–S16 全绿就忽略。其中有两个涉及 Runtime 最核心的承诺：同一个 RunId 不能重复执行，以及任何时候都不能错误释放别人的执行权。

### P1：同一个 RunId 的并发登记不是原子操作

当前逻辑是：

```
$existing = ReadJson "$queueDir\$RunId.json"
if ($existing) { ...拒绝... }

WriteJsonNoBom "$queueDir\$RunId.json" @{ ... }
```

这是先检查、再写入。两个相同 RunId 的请求可以同时读到“不存在”，随后都写入同一个队列文件。

这意味着当前的 `RUNID_INFLIGHT` 检查并不能严格保证重复 RunId 不会并发进入执行流程。

建议： 队列登记必须使用文件系统的独占创建语义，例如 `FileMode.CreateNew`，由创建成功的一方获得登记权；不能用普通的“检查文件是否存在，再写文件”代替原子占位。

还应增加一个真正并发的故障测试：两个进程同时以同一个 RunId 执行 acquire，必须严格只有一个成功。

### P1：release 的身份校验不完整

当前 release 有两个值得注意的分支：

- `owner.json` 不存在时，直接按传入 RunId 完成队列记录，没有验证队列记录中的 OwnerToken。
- `owner.json` 存在时，验证了 OwnerToken，却没有同时验证 `owner.runId` 是否等于传入的 RunId。

这与 Runtime 文档中“释放必须验证任务身份”的承诺不完全一致。

建议：

1. `owner.json` 存在时，同时验证 `runId + ownerToken`。
2. 再验证对应 queue 记录中的身份。
3. `lock` 仍存在但 `owner.json` 缺失时，不应直接当作已释放；应返回明确的 `OWNER_STATE_UNKNOWN` 或初始化状态。
4. 只有锁本身已经不存在时，才允许走真正的幂等释放分支。

这类检查不应依赖调用方“正常情况下不会传错”。

### P1：初始化超过 10 秒后，仍然可能误删活锁

当前初始化协议比 R12 好很多，但还没有完全解决根因：

```
if ($ageSec -lt $cfg.InitGraceSec) {
    return 'initializing'
}
return 'init_stalled'
```

也就是说，锁目录创建后，如果创建者在写 `owner.json` 前被系统长时间挂起，超过 `InitGraceSec = 10` 秒，其他等待者就会把它判为 `init_stalled` 并删除。

时间超过 10 秒，不等于创建者已经死亡。

这是 R13 当前最需要重新审视的设计点。初始化状态也必须能够识别创建者身份，或者在身份不可验证时采取 fail-closed 策略，不能仅靠固定时间自动回收。

### 另外三个 Runtime 问题

P1：Recovery 的 Java 进程匹配仍然偏宽。

目前不是按 Java 进程的真实身份定位，而是：

```
$_.CommandLine -match [regex]::Escape([string]$owner.pipelineTag)
```

`pipelineTag` 目前是 `make_api.js` 或 `patch_main.js`。这只能证明命令行包含这个字符串，不能证明它就是本次任务启动的 JVM。

例如，机器上另一个 Java 应用也通过 Nashorn 执行同名脚本，就可能被误杀。

建议记录本次启动的 JVM PID、ProcessStartTime，并验证完整脚本路径或唯一任务标识。恢复时只操作身份完全匹配的进程。

P2：队列等待者只记录 PID，没有记录进程启动时间。

Owner 已经使用 PID + StartTime 防止 PID 复用，但 queue 登记只写了：

```
ownerPid = $PID
```

`Is-OldestQueued` 也只通过 PID 是否存在判断等待者是否死亡。

如果等待者进程退出后 PID 被系统复用，旧队列项可能继续被当成活等待者，阻塞后续任务。

建议 queue 也保存 `ownerStart`，复用同一套进程身份判定逻辑。

P2：`ReadJson` 把损坏文件和文件不存在都变成 `$null`。

这会让 `Get-LockState` 无法区分：

- 创建者还没写完 owner 文件；
- owner 文件损坏；
- 文件读取失败；
- owner 文件确实不存在。

尤其是损坏文件超过 10 秒后，会进入 `init_stalled`，随后删除锁。这里应该增加 `owner_unknown` / `owner_corrupt` 一类状态。无法证明锁的所有者已经死亡，就不能自动回收。

还有一个我认为必须优先处理的测试安全问题：

测试副作用过大

`integration_runtime.ps1` 开始时执行：

```
Get-Process java -ErrorAction SilentlyContinue |
    Stop-Process -Force
```

这会杀掉机器上的所有 Java 进程，不只是 FineReport。

注释虽然说明这是测试环境清理，但脚本本身没有验证机器是否处于专用测试环境。用户在运行集成测试时，可能同时有其他 Java 服务。

建议改成只清理本测试明确创建、且身份经过验证的进程。不能把“测试前清空所有 Java”当成正常测试前置条件。

此外，测试文档存在同步问题：

- `integration_runtime.ps1` 实际有 S1–S16。
- `scripts/run-integration-tests.ps1` 仍写 S1–S15。
- `docs/architecture/runtime-supervisor.md` 也仍写 S1–S15。
- 统一门禁脚本和测试脚本仍硬编码 `D:\fineagent`。

这说明 R13 的配置单源化还没有覆盖整个测试与工具链。

### 但还发现两个跨模块问题

P1：Patch 的执行结果存在回归证据缺失时仍然通过的可能。

`application/contracts.js` 中：

```
function executionFromPatch(pj) {
  pj = pj || {};
  var mf = pj.manifest || {};
  var ok = pj.ok === true && mf.diffClean !== false;
  // ...
}
```

这里使用的是：

```
mf.diffClean !== false
```

这意味着 `diffClean` 缺失时也会被当成通过。

而 `fr_agent.ps1` 在没有找到 `manifest.json` 时，会把 `manifest` 设为 `$null`，随后仍然调用 `modify_report.js` 生成 Artifact。

因此，至少从这个契约函数看，存在这样的风险：

1. Patch 执行退出码为 0。
2. Manifest 缺失。
3. `executionFromPatch` 仍返回 `ok: true`。
4. 后续验收可能将它当成成功。

建议改为 fail-closed： Patch 成功必须同时满足 manifest 存在、结构有效、`diffClean === true`，以及规定的执行和渲染回归全部通过。缺少证据不能等同于证据通过。

这属于创作系统的可信度问题，我认为优先级不低于 Runtime。

P2：Planner 的术语归一化仍然有一个接口不匹配。

`semantic/model/registry.js` 产生的候选结构是：

```
{
  target: 'metric',
  ref: 'planned',
  confidence: 'high'
}
```

Resolver 原样返回候选。

但 `agent/tools/plan.js` 的 `normalizeTerm()` 使用：

```
r.candidates[0].name
```

我核对了 Registry 和 Resolver 的当前实现，候选并没有统一的 `name` 字段。

因此，当前这段归一化逻辑在 resolved 分支中无法取得预期的规范名称，最终会保留原始术语。

建议统一候选契约，明确 `target`、`ref`、`column` 分别代表什么，再由 Planner 工具层按照候选类型进行转换。不要简单给所有候选硬塞一个含义不明的 `name`。

这类问题很容易被标准英文名称的示例测试掩盖，建议增加中文 label → 规范指标名、中文 label → 规范维度名的端到端测试。

## 五、关于项目整体架构和 TS

这轮更新没有改变核心架构，也没有真正启动 TypeScript 迁移。

我仍然支持此前的方向：

TypeScript + 战略 DDD + 模块化单体。

但现在不建议把 TS 迁移和 R13 修复混在一起。特别是 `runtime.ps1`、FineReport Java 调用和 Nashorn 兼容边界，不应该因为上 TS 而重新设计。

当前几个重要模块的职责已经逐渐清楚：

- `lib/ir.js`：报表中间表示与校验。
- `lib/object.js`：FineReport 对象图构造。
- `semantic/*`：业务语义与 SQL 生成。
- `template/*`：模板检查、修改和回归。
- `application/*`：创作契约与能力声明。
- `agent/tools/*`：Agent 接口与执行编排。
- `runtime.ps1`：单实例 FineReport 执行权管理。

这比单纯按照文件类型划分目录更接近真正的领域边界。不过，`object.js` 依然是一个很大的核心模块，后续值得逐步拆分内部职责，但我不建议现在动它。

## 六、最终结论

整体方向认可

我对当前版本的评价是：

报表创作核心已经积累了相当多的实证能力，Runtime 也从简单的进程锁发展成了有状态、有恢复策略、有故障注入测试的 Supervisor。但还不能宣布 Runtime 正确性已经收口。

我尤其不希望你陷入一个循环：

发现一个并发问题 → 修复 → 增加测试 → 全绿 → 宣布收口 → 下一轮又发现基础协议存在竞态。

现在应该从继续增加测试数量，转向验证更底层的并发不变量。

我建议下一轮集中做一次 R14：Runtime 与 Artifact 双边界审查，先处理上面五个 P1，不增加新功能。验收时重点看三个性质：

1. 互斥安全性： 任何时刻最多只有一个 FineReport 执行权持有者。
2. 故障恢复安全性： 不能证明 Owner 已死亡，就绝不回收锁或终止 JVM。
3. 结果可信性： 没有完整执行和回归证据，就不能向 Agent 声明成功。

这三个性质真正站稳之后，R12/R13 才算完成了它们应该承担的职责。
