## 一、这次新增工作的实际价值

这次变化比前几轮大得多。前次审查基准 16c93bf → e4ae950，19 个提交。两件事：

- Agent 接入层和 Application 层开始有实际代码（不再只是架构设计）。
- FineReport 原生报表能力大幅扩展（图表装饰、条件属性、字典、页眉页脚、填报、子报表、条码等）。

项目重心变化：同时推进两条路线——① FineReport 报表表达能力；② 建立 Agent 可调用的报表操作接口。两条路线合理，但资源分配与架构关系值得重新审视。

## 二、发现的几个全局问题

### P1：Agent 工具层已落地，但还不是完整的 Agent API（优先修复）

涉及 agent/tools/fr_agent.ps1、agent/tools/*、application/。现有六 Verb：discover/resolve/compile/patch/validate/preview。三个问题：

- **问题 1：Planner 没有真正进入工具调用链。** semantic/planner/planner.js、capability.js 已有，但 fr_agent.ps1 没有 plan Verb。Agent 仍需自己拼接各能力。建议补 plan（input: ReportIntent → output: status ready|ambiguous|rejected + reportSpec + assumptions + unresolvedQuestions + validationWarnings）。不需要再开发 Agent，只需把已有 Planner 接到工具层。
- **问题 2：Create/Modify 业务命名未统一。** 底层叫 compile/patch 没问题，但 Agent 最好有统一业务入口（create/modify），保留底层 Verb 为内部实现。
- **问题 3：Discover 能力清单不完整。** 未表达：指标计算语义/能否聚合/关系连接约束/运行环境实际能力/需用户确认条件/运行期与编译期能力区别。建议未来升级为 CapabilityManifest，不必立即引入复杂 Registry。

### P1：ReportArtifact v1 存在真实的可靠性问题（本轮最值得修复）

① **Artifact ID 不真正唯一**：`artifactId: sourceType + ':' + (parts.outName || 'unknown')`——同报表重复创建 ID 不变。建议引入 runId。

② **固定文件路径并发污染**：所有调用共用 logs/agent/compile.json、patch.json、validate.json、artifact.json——两任务并发时 A 可能读到 B 的结果。建议 `logs/agent/runs/{runId}/` 独立目录。

③ **Preview/Validation 陈旧数据风险**：create_report.js 读已有 preview.json——当前任务没跑 preview 时上一个任务的预览可能进当前 Artifact；validation 虽需 AGENT_WITH_VALIDATION=1，但没用 runId 验证 validate.json 属于当前任务。

④ **PowerShell 返回码可能掩盖 Artifact 失败**：compile/patch 分支 `$okAll = ($rc -eq 0) -and ($artRc -eq 0)` 计算后**最终 exit $rc**——Compiler 成功+Artifact 失败时 JSON ok=false 但 exit 0。应 `exit $(if ($okAll) { 0 } else { 1 })`；validate 分支也应检查 Artifact 刷新结果。

### P1：IR 能力声明存在不一致

`supported = 已构建且经真实渲染/回归验证` 自定口径 vs 图表装饰实际状态（stack/label/conditionalSeries 标 supported 但注记"渲染端待达"）——**构造能力与渲染能力未严格分开**。Agent 看 discover 以为堆叠图已支持，实际只是对象挂接完成。建议四层状态：API 构造成功 / CPT 序列化成功 / FineReport 实际渲染正确 / Agent 可安全使用（不必采用特定 JSON 结构，但必须区分）。

### P2：覆盖率看板统计口径不够严谨

coverage_report.js 以类名出现在源码/Token 命中/Carrier 文件存在为准——类名出现≠功能正确实现、Carrier 存在≠通过该功能独立引擎回归；GATES 是共享全局门禁而非每能力独立测试记录。建议拆两种指标：**API 覆盖**（已识别/已接入/未接入的类）与**产品能力覆盖**（已构造/已序列化/已渲染/已回归），不要混成一个百分比。coverage 中仍有「(漏账：批排期时人工归入)」说明自动分类未闭环——防覆盖率数字误导决策。

**架构红线提醒**：两个系统——A：FineReport 编译与表达引擎（IR/Object/CPT/Runtime）；B：AI 报表创作平台（Agent/Planner/Semantic/Application/Artifact）——需要协同但不该互相侵入：图表后端不应关心 Agent 如何规划；Agent 工具不应知道 VanChart 的 Java 对象结构。此分界应成为今后架构红线。

## 四、建议：下一轮不要继续批量扩展功能

连续 A–J 批后若继续批 K/L/M，可能出现：FineReport 能力越来越丰富，但 Agent 只能用其中很小一部分。建议改为：

### r9（本轮执行）：Agent 创作链可靠性收口

- **r9-A Artifact 可靠性**（P1）：runId、独立任务目录、防陈旧结果、PowerShell 退出码、原子写入。验收：两个并发任务互不污染；任何 Artifact 生成失败都不能返回成功。
- **r9-B CapabilityManifest**（P1）：统一 IR、Spec、Object、真实渲染能力状态。验收：Agent 不会把仅完成对象挂接的功能宣传为已完整支持。
- **r9-C Planner 接入**（P1）：把已有 Planner 接入 Agent Tool API，形成 plan → compile → validate → preview。验收：Agent 能通过工具获得 ready/ambiguous/rejected 三种明确结果。
- **r9-D 真实任务闭环**（P1）：选生产日报、图表报表、已有模板修改三场景。验收：从自然语言到最终 CPT，Agent 不需要人工编写 JSON 中间产物。

## 五、关于批 J 的建议

PolyWorkSheet 结论值得保留，但不要立即投入大量精力攻克剩余全部 FineReport API。建议建立产品价值优先级：普通二维表/分组/合计（极高）、参数筛选排序（极高）、条件格式（极高）、常见图表（高）、模板修改（极高）、子报表钻取（高）、填报（中，取决于业务）、地图特殊图表（低）、PolyWorkSheet（低）。用户不会因为支持 223 种 Java 类就认为 AI 能创建 223 种业务报表——用户关心能不能完成自己的工作。

## 六、最终评价

| 领域 | 结论 |
| --- | --- |
| 底层编译器 | 进展显著 |
| FineReport API 覆盖 | 扩展显著 |
| Agent 工具接口 | 已落地 |
| Artifact 可靠性 | **需要修复** |
| 能力声明准确性 | **需要统一** |
| 自主创作闭环 | 仍需加强 |

三个坚持原则：① FineReport API 可持续探索，但只有经真实验证的能力才能进正式能力清单；② Agent 永远只操作业务级契约，不直接操作底层 Java 对象；③ 所有生成和修改操作必须能独立追踪、验证和交付。

建议：先执行 r9-A、r9-B，再接 Planner。**暂时冻结新的大规模 API 扩展**。下一步应证明它能可靠地完成工作，而不是继续证明它能调用更多 API。
